Why Automation?

For many years, most system administration and infrastructure management has relied on manual tasks performed through graphical or command-line user interfaces. This approach is error-prone and difficult to scale.

The Problem with Manual Administration

System administrators often work from checklists, other documentation, or a memorized routine to perform standard tasks. This traditional approach has several significant drawbacks:

❌
Error-Prone Process

It's easy for a system administrator to skip a step or make a mistake on a step. Verification that steps were performed properly is often limited.

🔀
Configuration Drift

Managing each server manually and independently makes it very easy for many servers to be different in minor (or major) ways, leading to inconsistent environments.

⏰
Time-Consuming

Manual tasks take valuable time away from more critical work and don't scale well as your infrastructure grows.

How Automation Helps

AutomationThe use of technology to perform tasks with reduced human intervention. In IT, this typically means using scripts or tools to automate repetitive system administration tasks. can help avoid the problems caused by manual system administration and infrastructure management. As a system administrator, you can use automation to ensure that all your systems are quickly and correctly deployed and configured.

Key Benefits of Automation

  • Consistency: Ensure all systems are configured identically every time
  • Speed: Deploy and configure systems in minutes instead of hours
  • Scale: Manage hundreds or thousands of systems with the same effort as one
  • Documentation: Your automation code serves as documentation for your infrastructure
  • Version Control: Track changes to your infrastructure over time

Infrastructure as Code

A good automation system allows you to implement Infrastructure as CodeA practice where infrastructure configuration is written as machine-readable definition files rather than through interactive configuration tools. This allows infrastructure to be versioned, tested, and deployed automatically. practices. This means that you can use a machine-readable automation language to define and describe the required state of your IT infrastructure.

Mitigating Human Error

Reducing the number of tasks performed manually on servers by using task automation and Infrastructure as Code practices can help ensure that your servers are consistently configured more often.

⚠️ Important Consideration

You need to become accustomed to making changes by updating your automation code, rather than manually applying them to your servers. Otherwise, you run the risk of losing manually applied changes the next time you apply changes using automation.

You can use code review, peer review by multiple subject matter experts, and document the procedure within the automation content to reduce your operational risks. Ultimately, you can enforce that changes to your IT infrastructure be made through automation to mitigate human error.

What is Ansible?

Ansible is an open source automation platform. It is a simple automation language that can accurately describe an IT application infrastructure in Ansible Playbooks. It is also an automation engine that runs Ansible Playbooks.

Ansible at a Glance

Ansible can manage powerful automation tasks and can adapt to many workflows and environments. At the same time, new users of Ansible can very quickly use it to become productive.

📝
Ansible Is Simple

Ansible PlaybooksYAML files that contain a series of plays. Each play targets specific hosts and defines tasks to be executed. Playbooks are the heart of Ansible's configuration, deployment, and orchestration language. provide human-readable automation. This means that playbooks are automation tools that are also easy for humans to read, comprehend, and change. No special coding skills are required to write them.

💪
Ansible Is Powerful

You can use Ansible to deploy applications for configuration management, for workflow automation, and for network automation. You can use Ansible to orchestrate the entire application lifecycle.

🚫
Ansible Is Agentless

Ansible is built around an agentless architectureAn architecture where managed hosts don't need any special software installed. Ansible connects via standard protocols (SSH for Linux, WinRM for Windows) and pushes small programs called modules to perform tasks, removing them when done.. Typically, Ansible connects to the hosts it manages by using OpenSSH or WinRM and runs tasks.

Ansible Strengths

Ansible has a number of important strengths that make it the preferred choice for automation:

Strength Description
Cross Platform Support Ansible provides agentless support for Linux, Windows, UNIX, and network devices, in physical, virtual, cloud, and container environments.
Human-Readable Automation Ansible Playbooks, written as YAMLYAML Ain't Markup Language - a human-readable data serialization format commonly used for configuration files. Ansible uses YAML for playbooks because of its simplicity and readability. text files, are easy to read and help ensure that everyone understands what they do.
Precise Application Descriptions Every change can be made by Ansible Playbooks, and every aspect of your application environment can be described and documented.
Easy to Manage in Version Control Ansible Playbooks and projects are plain text. They can be treated like source code and placed in your existing version control system.
Support for Dynamic Inventories The list of machines that Ansible manages can be dynamically updated from external sources to capture the correct, current list of all managed servers.
Orchestration That Integrates Easily HP SA, Puppet, Jenkins, Red Hat Satellite, and other systems can be leveraged and integrated into your Ansible workflow.

The Ansible Way

The following goals were used during the design of Ansible:

1
Complexity Kills Productivity

Simpler is better. Ansible is designed so that its tools are simple to use and automation is simple to write and read. You should take advantage of this to strive for simplification in how you create your automation.

2
Optimize for Readability

The Ansible automation language is built around simple, declarative, text-based files that are easy for humans to read. Written properly, Ansible Playbooks can clearly document your workflow automation.

3
Think Declaratively

Ansible is a desired-state engineA system that describes the end state you want your systems to be in, rather than the steps needed to get there. Ansible determines what changes need to be made to reach that state.. It approaches the problem of how to automate IT deployments by expressing them in terms of the state that you want your systems to be in.

💡 Best Practice

The goal of Ansible is to put your systems into the desired state, only making changes that are necessary. Trying to treat Ansible like a scripting language is not the right approach—think declaratively about the end state you want to achieve.

Key Components

Control Node

The control nodeThe machine where Ansible is installed and from which automation is run. This machine has copies of your Ansible project files and is used to execute playbooks against managed hosts. is the machine where Ansible is installed and run from. This machine also has copies of your Ansible project files. Python 3.8 or later needs to be installed on the control node before installing the ansible-core package.

Managed Hosts

Managed hostsThe systems that Ansible manages. These systems don't need to have Ansible installed—they only need to allow the control node to connect to them, typically via SSH (Linux) or WinRM (Windows). are listed in an inventoryA file or script that defines the managed hosts and groups them for collective management. Inventories can be static (defined in a text file) or dynamic (generated by scripts from external sources)., which also organizes those systems into groups for easier collective management.

Plays and Playbooks

Instead of writing complex scripts, Ansible users create high-level playsA play targets specific hosts and defines a series of tasks to execute on them. Plays map a group of hosts to well-defined roles or tasks. to ensure that a host or group of hosts is in a particular state. A play performs a series of tasksAn action that Ansible performs on managed hosts. Tasks call modules with specific arguments to achieve a desired state. on the hosts, in the order specified by the play.

Example Playbook Structure
# site.yml - Example Ansible Playbook
---
- name: Configure web servers
  hosts: webservers
  become: true
  
  tasks:
    - name: Install Apache web server
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Start and enable Apache
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

Modules

Each task runs a moduleA small piece of code (typically written in Python) that Ansible pushes to managed hosts to perform a specific task. Modules are the tools in your toolkit—there are hundreds available for different automation tasks., a small piece of code (written in Python, PowerShell, or some other language), with specific arguments. Each module is essentially a tool in your toolkit. Ansible ships with hundreds of useful modules that can perform a wide variety of automation tasks.

Idempotence

Tasks, plays, and playbooks are designed to be idempotentThe property where running an operation multiple times produces the same result as running it once. In Ansible, this means you can safely run a playbook multiple times—if systems are already in the correct state, no changes are made.. This means that you can safely run a playbook on the same hosts multiple times. When your systems are in the correct state, the playbook makes no changes when you run it.

ℹ️ Note on Idempotence

Numerous modules are available that you can use to run arbitrary commands. However, you must use those modules with care to ensure that they run in an idempotent way. The goal is that running a playbook multiple times should not cause unintended side effects.

Agentless Architecture

The Ansible architecture is agentless. Typically, when an administrator runs an Ansible Playbook, the control node connects to the managed host by using SSH (by default) or WinRM. This means that you do not need to have an Ansible-specific agent installed on managed hosts, and do not need to permit any additional communication between the control node and managed hosts.

Agent-Based Tools

• Require agent software on each managed host
• Need to maintain and update agents
• Additional ports/firewall rules needed
• More complex security considerations

Ansible (Agentless)

✓ No agent installation required
✓ Uses existing SSH/WinRM infrastructure
✓ Standard ports already permitted
✓ More efficient and secure

Common Use Cases

Community Ansible Package

Ansible Core in Red Hat Enterprise Linux

Red Hat provides Ansible Core as an RPM package, ansible-core, included with Red Hat Enterprise Linux 9 in the AppStream repository. It is intended to enable support for automation code provided or generated by Red Hat.

⚠️ Scope of Support

The scope of support is limited to any Ansible Playbooks, roles, or modules that are included with or generated by a Red Hat product, such as the system roles included in the rhel-system-roles package, Red Hat Insights remediation playbooks, and OpenSCAP compliance Ansible Playbooks. Other use cases, including using the other Ansible modules and plug-ins included with Ansible Core 2.13, are outside the scope of support.

Red Hat Ansible Automation Platform

Red Hat provides a fully supported version of Ansible through Red Hat Ansible Automation PlatformA fully supported version of Ansible that enables enterprises to manage their automation at scale. It includes official support, certified content, on-premise tools, and cloud services.. This platform provides a supported version of the Ansible Core toolset plus additional certified and supported content, tools, components, and cloud services.

Installing Ansible

To run Ansible Playbooks, install automation content navigator (ansible-navigator) on your control node and download an execution environment.

Preparing a Control Node

Hosts that are managed by Ansible do not need to have ansible-navigator installed; you only need to install that tool on the control node from which you run Ansible Playbooks. Python 3.8 or later needs to be installed on the control node before installing the ansible-core package.

⚠️ Subscription Required

You need a valid Red Hat Ansible Automation Platform subscription to install automation content navigator on your control node. If you have activated Simple Content Access for your organization in the Red Hat Customer Portal, then you do not need to attach the subscription to your system.

Preparing Managed Hosts

One of the benefits of Ansible is that managed hosts do not need to have a special agent installed. The Ansible control node connects to managed hosts by using a standard network protocol to ensure that the systems are in the specified state.

ℹ️ Managed Host Requirements

Managed hosts might have some requirements depending on how the control node connects to them and what modules are run on them:

  • Python installed: Linux and UNIX managed hosts need to have Python installed for most modules to work. The version of Python to use depends on the version of the ansible-core package.
  • SELinux support: If SELinux is enabled on the managed hosts, ensure that the python3-libselinux package is installed before using modules related to copy, file, or template functions.
  • SSH connectivity: Ansible needs to be able to connect to the machine by using SSH, and if it connects as a regular user it needs to be able to use a mechanism such as sudo to get superuser access.

Microsoft Windows and Network Devices

Ansible also supports managing Microsoft Windows systems and network devices:

Microsoft Windows

• Uses the ansible.windows Content Collection
• Requires PowerShell 3.0 or later
• Requires .NET Framework 4.0 or later
• Connects via WinRM

Network Devices

• Support for Cisco IOS, IOS XR, NX-OS
• Juniper Junos, Arista EOS, VyOS
• Modules run on control node
• Uses CLI, XML, or API over SSH/HTTPS
