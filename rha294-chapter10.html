Add a task that installs redis only if the managed host's total swap spaceVirtual memory area on disk used when physical RAM is full. ansible_facts['swaptotal_mb'] contains this value in megabytes. is greater than 10 MB, using an Ansible fact in the when condition.

8

Troubleshoot verify_user.yml

The existing verify_user.yml playbook is supposed to verify that the sam user was created — without creating it if missing. Run it with --check and fix any errors found.

Error 1: Module Name Typo

🔴 Error

Running with --check shows: ERROR! couldn't resolve module/action 'ansible.buildin.user'

The module is misspelled: ansible.buildin.user → should be ansible.builtin.user

✅ Fix

Correct the spelling from ansible.buildin.user to ansible.builtin.user

Error 2: Indentation Error on when

🔴 Error

After fixing the module name, running again shows: Unsupported parameters for (ansible.builtin.lineinfile) module: when.

The when clause is indented under the module parameters instead of at the task level.

✅ Corrected verify_user.yml
~/review-cr1/verify_user.yml — Corrected
---
- name: Verify the sam user was created
  hosts: dev

  tasks:

    - name: Verify the sam user exists
      ansible.builtin.user:
        name: sam
      check_mode: true
      register: sam_check

    - name: Sam was created
      ansible.builtin.debug:
        msg: "Sam was created"
      when: sam_check['changed'] == false

    - name: Output sam user status to file
      ansible.builtin.lineinfile:
        path: /home/student/verify.txt
        line: "Sam was created"
        create: true
      when: sam_check['changed'] == false

Architecture Overview

📐 Three-Playbook Design

This lab demonstrates a modular approach where a master site.yml imports specialized sub-playbooks. This pattern is common in production automation.

FileTarget HostsPurpose
dev_deploy.ymlwebservers groupInstall httpd, deploy config, copy content, open firewall
get_web_content.ymlworkstationVerify web server serves content; log failures
site.yml(imports both)Master playbook — runs both in order

Key Specifications

  • One play targeting webservers group with become: true
  • Task: Install the httpd package
  • Task: Start httpd service, enable on boot
  • Task: Deploy templates/vhost.conf.j2 → /etc/httpd/conf.d/vhost.conf, notify Restart httpd handler
  • Task: Copy files/index.html → /var/www/vhosts/{{ ansible_facts['hostname'] }}/ (create dir if missing)
  • Task: Open firewall for httpd service using ansible.posix.firewalld
  • Handler: "Restart httpd" restarts the httpd service
  • One play named "Test web content" targeting workstation with become: true
  • Block/rescue task named "Retrieve web content and write to error log on failure"
  • Block: Task "Retrieve web content" uses ansible.builtin.uri to GET http://servera.lab.example.com, register as content
  • Rescue: Task "Write to error file" writes content to /home/student/review-cr2/error.log, creating file if missing
  • Uses ansible.builtin.import_playbook (not include) for deterministic ordering
  • Imports dev_deploy.yml first, then get_web_content.yml
  • Run this to verify both playbooks work end-to-end

Play Header & httpd Install Task

Start and Enable the httpd Service

Add to tasks:
    - name: Start httpd service
      ansible.builtin.service:
        name: httpd

3

Deploy Jinja2 Template with Handler Notification

The ansible.builtin.template module renders the .j2 file and deploys it. The notify directive triggers the handler only when the task reports changed.

Template deploy task
    - name: Deploy configuration template
      ansible.builtin.template:
        src: templates/vhost.conf.j2
        dest: /etc/httpd/conf.d/vhost.conf
        owner: root
        group: root
        mode: '0644'
      notify: Restart httpd
4

Copy index.html to Hostname-Based Directory

The destination uses ansible_facts['hostname'] to create host-specific vhost directories. The src ending in / copies directory contents, not the directory itself.

Copy task
    - name: Copy index.html
      ansible.builtin.copy:
        src: files/
        dest: "/var/www/vhosts/{{ ansible_facts['hostname'] }}/"
        owner: root
        group: root
        mode: '0644'
5

Open Firewall for HTTP Service

Firewalld task
    - name: Ensure web server port is open
      ansible.posix.firewalld:
        state: enabled
        permanent: true
        immediate: true
        service: http
6

Add the Handler

Handlers appear in the handlers: section (same indentation level as tasks:). The handler name must exactly match the string in notify:.

Handler section (add after tasks)
  handlers:

    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted
💡 Handler Behavior

Handlers only run when notified AND the notifying task reported changed. They run at the end of the play regardless of how many tasks notify the same handler — it only runs once.

Lab 2: get_web_content.yml & site.yml

get_web_content.yml — Block/Rescue Pattern

This playbook demonstrates Ansible's error-handling with block/rescueBlock groups tasks; if any block task fails, Ansible runs the rescue section instead (like try/except). An optional always section runs in all cases.. It retrieves content from the web server and logs any failures.

~/review-cr2/get_web_content.yml
---
- name: Test web content
  hosts: workstation
  become: true

  tasks:

    - name: Retrieve web content and write to error log on failure
      block:

        - name: Retrieve web content
          ansible.builtin.uri:
            url: http://servera.lab.example.com
            return_content: true
          register: content

      rescue:

        - name: Write to error file
          ansible.builtin.lineinfile:
            path: /home/student/review-cr2/error.log
            line: "{{ content }}"
            create: true

site.yml — The Master Playbook

The ansible.builtin.import_playbook module statically imports playbooks at parse time, ensuring deterministic ordering and full variable resolution.

~/review-cr2/site.yml
---
- name: Deploy web servers
  ansible.builtin.import_playbook: dev_deploy.yml

- name: Retrieve web content
  ansible.builtin.import_playbook: get_web_content.yml
⚠️ import_playbook vs include_playbook

import_playbook is static — it's processed at parse time, making all plays visible to --list-tasks. include_playbook is dynamic (runtime). For the exam and this lab, use import_playbook for reliable, predictable behavior.

Lab 3: Storage Role & LVM Configuration

storage.yml — LVM with System Role

The rhel_system_roles.storageA RHEL system role that abstracts complex storage operations. It creates/manages volume groups, logical volumes, filesystems, and mount points using a single declarative variable (storage_pools). role manages the entire LVM stack from a single storage_pools variable.

~/review-cr3/storage.yml — Complete
---
- name: Configure storage on webservers
  hosts: webservers

  roles:
    - name: redhat.rhel_system_roles.storage
      storage_pools:
        - name: vg_web
          type: lvm
          disks:
            - /dev/vdb
          volumes:
            - name: lv_content
              size: 128m
              mount_point: "/var/www/html/content"
              fs_type: xfs
              state: present

            - name: lv_uploads
              size: 256m
              mount_point: "/var/www/html/uploads"
              fs_type: xfs
              state: present

Storage Role Concepts

LVM Hierarchy

Physical Volume (PV) → /dev/vdb — The actual disk or partition registered with LVM

Volume Group (VG) → vg_web — A pool of storage aggregated from one or more PVs

Logical Volume (LV) → lv_content, lv_uploads — Flexible partitions carved from the VG

Filesystem → XFS formatted on each LV and mounted persistently

typelvmUse LVM backend
disks/dev/vdbSource physical device(s)
volumes[].size128m, 256mLV size in mebibytes
volumes[].mount_point/var/www/html/...Where to mount persistently
volumes[].fs_typexfsFilesystem format
volumes[].statepresentCreate if not exists

Lab 3: Users, Sudo & Ansible Vault

dev-users.yml — Create developer User with Sudo

This playbook creates the developer user in the webdev group, with a hashed password from an Ansible VaultAnsible Vault encrypts sensitive data at rest. The pass-vault.yml file contains the pwhash variable (a password hash) encrypted with the vault password 'redhat'.-encrypted file, and configures passwordless sudo for the group.

~/review-cr3/dev-users.yml — Complete
---
- name: Create local users
  hosts: webservers
  vars_files:
    - pass-vault.yml

  tasks:

    - name: Add webdev group
      ansible.builtin.group:
        name: webdev
        state: present

    - name: Create user accounts
      ansible.builtin.user:
        name: developer
        groups: webdev
        password: "{{ pwhash }}"

    - name: Modify sudo config to allow webdev members sudo without a password
      ansible.builtin.lineinfile:
        path: /etc/sudoers.d/webdev
        state: present
        create: true
        mode: '0440'
        line: "%webdev ALL=(ALL) NOPASSWD: ALL"
        validate: /usr/sbin/visudo -cf %s

Key Concepts Explained

vars_files loads external variable files into the play scope. The pass-vault.yml file is encrypted with Ansible Vault and contains the pwhash variable — a pre-hashed password string generated by the lab setup. You must supply the vault password (redhat) when running the playbook.

⚠️ Never Store Plain Passwords

The password parameter of ansible.builtin.user expects a hashed password (not plaintext). The pwhash variable from the vault file contains the pre-computed hash.

The validate parameter runs a command against a temp copy of the file before writing it. The %s is replaced by the temp file path. This prevents writing a broken sudoers file that could lock out sudo access.

validate pattern
# visudo -cf checks sudoers syntax
# %s is replaced by the temp file Ansible creates before committing
validate: /usr/sbin/visudo -cf %s

The mode: '0440' sets sudoers file permissions (read-only for owner and group, no world access) — the standard for /etc/sudoers.d/ files.

Understanding the Ansible Role Structure

Roles follow a convention-over-configurationA design principle where sensible defaults eliminate the need for explicit configuration. Ansible automatically looks in standard role subdirectories (tasks/, handlers/, templates/, etc.) without needing to specify paths. pattern. Ansible automatically discovers content in these standard subdirectories:

DirectoryContainsAuto-loaded?
tasks/main.ymlMain list of tasks for the role✅ Yes
handlers/main.ymlHandler definitions✅ Yes
defaults/main.ymlDefault variable values (overrideable)✅ Yes
vars/main.ymlRole variables (NOT overrideable by inventory)✅ Yes
templates/Jinja2 template files (.j2)✅ Yes (by template module)
files/Static files for copy/script modules✅ Yes (by copy module)
meta/main.ymlRole metadata: author, description, dependencies✅ Yes
tests/Test inventory and playbook (optional)❌ Manual only
README.mdRole documentation❌ Documentation only

defaults/ vs vars/ — A Critical Distinction

Both directories store variables, but they have very different precedence levels:

LocationPrecedenceCan Be Overridden ByUse Case
defaults/main.ymlLowest (1)Everything — inventory, play vars, extra-varsSensible defaults users should customize
vars/main.ymlHigh (16)Only extra-vars (-e flag)Internal role constants that should NOT be changed
💡 Lab 4 uses defaults/

In this lab, all role variables go into defaults/main.yml because they represent configurable values (web_package, web_service, etc.) that a user might legitimately want to override for a different web server. The vars/ directory is removed since it's unused.

Two Ways to Use a Role in a Playbook

Method 1: roles: key (classic, used in this lab)
---
- name: Apply the ansible-httpd role
  hosts: webdev
  roles:
    - ansible-httpd
Method 2: ansible.builtin.include_role in tasks: (dynamic)
---
- name: Apply the ansible-httpd role
  hosts: webdev
  tasks:
    - name: Apply httpd role
      ansible.builtin.include_role:
        name: ansible-httpd

The roles: key runs before regular tasks. Using include_role in tasks: runs at the point where it appears, giving you more control over ordering.

Reading the PLAY RECAP

At the end of every playbook run, Ansible prints a recap line per host:

PLAY RECAP format explained
PLAY RECAP ***********************
servera.lab.example.com  : ok=4  changed=2  unreachable=0  failed=0  skipped=1  rescued=0  ignored=0

# ok=N      → Total tasks that ran (including unchanged)
# changed=N → Tasks that made actual changes
# failed=N  → Must be 0 for the playbook to pass lab grading
# skipped=N → Tasks skipped via 'when' conditions — normal and expected
# rescued=N → Tasks handled by a 'rescue' clause
# ignored=N → Tasks with ignore_errors: true that failed
💡 Idempotency Check

Run any playbook a second time on the same hosts. A properly written playbook should show changed=0 on the second run — everything is already in the desired state. This property is called idempotencyAn idempotent operation produces the same result whether run once or many times. Well-written Ansible playbooks are idempotent — they make changes only when the system is not already in the desired state. and is a key Ansible design principle.

EX294 Exam Tips

🎯 Exam Strategy 1: Always use FQCN

Use fully-qualified collection names for all modules: ansible.builtin.dnf, not just dnf. This ensures your playbooks work regardless of collection configuration.

🎯 Exam Strategy 2: Verify with --check first

Before running any playbook on the exam, run with --check and --syntax-check to catch errors. Fix issues before making actual changes to the managed hosts.

🎯 Exam Strategy 3: Run lab grade frequently

The lab grade command tells you exactly which items pass and fail. Run it after completing each task, not just at the end. Fix failures immediately while the context is fresh.

🎯 Exam Strategy 4: Idempotency is your friend

Running a correct playbook twice should show changed=0 on the second run. If it doesn't, your playbook is not idempotent — investigate why and fix it.

🎯 Exam Strategy 5: Indentation is everything in YAML

The most common errors on the exam are indentation mistakes. Use consistent 2-space indentation. Remember: when:, loop:, register:, and notify: must be at the task level, not inside module parameters.
