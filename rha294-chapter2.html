What is a Playbook?

Playbooks are Ansible's configuration, deployment, and orchestration language, expressed in YAML format.

Ad-hoc Commands vs. Playbooks

While ad-hoc commandsSingle-line Ansible commands executed directly from the command line. Useful for quick, one-time tasks but not reusable or version-controllable. are useful for quick tasks, playbooksYAML files containing one or more plays that define automation tasks. Playbooks are reusable, version-controllable, and can express complex multi-step workflows. provide a more powerful and flexible approach.

Feature Ad-hoc Commands Playbooks
ReusabilityNot easily reusableHighly reusable
Version ControlDifficult to trackEasy to version with Git
ComplexitySingle tasks onlyMulti-step workflows
VariablesLimited supportFull variable support
ConditionalsNot supportedFull conditional logic
DocumentationNoneSelf-documenting

💡 Key Concept

A playbook contains plays. Each play targets a group of hosts and contains tasks. Each task calls a module to perform an action.

YAML Syntax

YAML (YAML Ain't Markup Language) is a human-readable data serialization format used for Ansible playbooks.

YAML Basics

📏
Indentation
Use spaces only (never tabs). Standard is 2 spaces per level.
🔑
Key-Value Pairs
Format: key: value with a space after the colon.
📋
Lists
Items start with a dash and space: - item

Data Types

YAML data types 
# Strings
name: Configure webserver
quoted: "String with: special chars"

# Numbers
port: 80
timeout: 30.5

# Booleans
enabled: true
debug: false

# Lists
packages:
  - httpd
  - firewalld
  - mod_ssl

# Dictionaries
server:
  hostname: web1
  ip: 192.168.1.10
⚠️ Common Mistakes

Tabs: Never use tabs - YAML requires spaces only.
Colons: Values with colons need quotes: "http://example.com"
Variables: Values starting with {{ must be quoted.

Playbook Structure

Understanding the anatomy of a playbook is essential for writing effective automation.

Complete Playbook Example

webserver.yml 
---
- name: Configure web servers       # Play name
  hosts: webservers                   # Target hosts
  become: true                        # Privilege escalation

  vars:                                # Play variables
    http_port: 80
    doc_root: /var/www/html

  tasks:                               # Task list
    - name: Install Apache
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Start and enable httpd
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

  handlers:                            # Handler list
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Play Attributes

AttributeRequiredDescription
nameRecommendedDescriptive name for the play
hostsYesTarget hosts or groups from inventory
becomeNoEnable privilege escalation (sudo)
varsNoDefine variables for the play
tasksNo*List of tasks to execute
handlersNoTasks triggered by notifications

Host Patterns

Common host patterns
hosts: all                      # All hosts in inventory
hosts: webservers               # Single group
hosts: webservers:dbservers     # Multiple groups (OR)
hosts: webservers:&dbservers    # Intersection (AND)
hosts: webservers:!staging      # Exclude group
hosts: web1.example.com        # Single host
hosts: *.example.com           # Wildcard

Working with Modules

Modules are the building blocks of Ansible tasks, providing specific functionality for different automation needs.

Fully Qualified Collection Names (FQCNs)

Always use FQCNsFully Qualified Collection Name - the complete path to a module including namespace, collection, and module name. Example: ansible.builtin.copy for clarity and to avoid naming conflicts:

# Recommended: FQCN
ansible.builtin.copy:
  src: file.txt
  dest: /tmp/file.txt

# Not recommended: short name
copy:
  src: file.txt
  dest: /tmp/file.txt

Essential Modules Reference

ansible.builtin.copy
Collection: ansible.builtin
Copy files from the control node to managed hosts.
- name: Copy configuration file
  ansible.builtin.copy:
    src: files/httpd.conf
    dest: /etc/httpd/conf/httpd.conf
    owner: root
    group: root
    mode: '0644'
ansible.builtin.file
Collection: ansible.builtin
Manage file and directory properties.
- name: Create directory
  ansible.builtin.file:
    path: /var/www/html
    state: directory
    mode: '0755'
ansible.builtin.template
Collection: ansible.builtin
Process Jinja2 templates and copy to managed hosts.
- name: Deploy config from template
  ansible.builtin.template:
    src: templates/httpd.conf.j2
    dest: /etc/httpd/conf/httpd.conf
ansible.builtin.dnf
Collection: ansible.builtin
Manage packages with DNF (RHEL 8+, Fedora).
- name: Install packages
  ansible.builtin.dnf:
    name:
      - httpd
      - firewalld
    state: present

- name: Update all packages
  ansible.builtin.dnf:
    name: "*"
    state: latest
ansible.builtin.yum
Collection: ansible.builtin
Manage packages with YUM (RHEL 7 and earlier).
- name: Install package with yum
  ansible.builtin.yum:
    name: httpd
    state: present
ansible.builtin.service
Collection: ansible.builtin
Manage services (works with multiple init systems).
- name: Start and enable httpd
  ansible.builtin.service:
    name: httpd
    state: started
    enabled: true
ansible.posix.firewalld
Collection: ansible.posix
Manage firewalld rules and zones.
- name: Allow HTTP through firewall
  ansible.posix.firewalld:
    service: http
    permanent: true
    state: enabled
    immediate: true
ansible.builtin.user
Collection: ansible.builtin
Manage user accounts.
- name: Create application user
  ansible.builtin.user:
    name: appuser
    uid: 1050
    group: appgroup
    shell: /bin/bash
    state: present
ansible.builtin.group
Collection: ansible.builtin
Manage groups.
- name: Create application group
  ansible.builtin.group:
    name: appgroup
    gid: 1050
    state: present
ansible.builtin.command
Collection: ansible.builtin
Execute commands on targets. Safe but limited (no shell features).
- name: Run a command
  ansible.builtin.command:
    cmd: /usr/bin/myapp --init
    creates: /opt/myapp/.initialized
ansible.builtin.shell
Collection: ansible.builtin
Execute commands through the shell. Supports pipes, redirects.
- name: Run shell command
  ansible.builtin.shell:
    cmd: cat /var/log/messages | grep error | wc -l
  register: error_count
  changed_when: false
⚠️ Caution

Use command and shell sparingly. They are not idempotent by default. Prefer purpose-built modules when available.

ansible.builtin.debug
Collection: ansible.builtin
Print statements during execution for debugging.
- name: Display variable
  ansible.builtin.debug:
    msg: "Port is {{ http_port }}"

Variables in Playbooks

Variables make your playbooks flexible and reusable by parameterizing configuration values.

Why Use Variables?

🔄
Reusability
Write once, use everywhere with different values for each environment.
🔒
Security
Keep sensitive data separate from playbook code.
📋
Maintainability
Change values in one place instead of searching through code.

Defining Variables

1. Play-Level Variables (vars)

Variables in play
---
- name: Configure web server
  hosts: webservers
  
  vars:
    http_port: 80
    doc_root: /var/www/html
    packages:
      - httpd
      - mod_ssl

  tasks:
    - name: Install packages
      ansible.builtin.dnf:
        name: "{{ packages }}"
        state: present

2. External Variable Files (vars_files)

vars/webserver.yml
---
http_port: 80
doc_root: /var/www/html
admin_email: admin@example.com
Playbook using vars_files
---
- name: Configure web server
  hosts: webservers
  
  vars_files:
    - vars/webserver.yml

  tasks:
    - name: Display port
      ansible.builtin.debug:
        msg: "HTTP port is {{ http_port }}"

3. Command Line Variables

Passing variables at runtime
# Single variable
$ ansible-playbook site.yml -e "http_port=8080"

# Multiple variables
$ ansible-playbook site.yml -e "http_port=8080 env=production"

# Variables from file
$ ansible-playbook site.yml -e @vars/production.yml

Using Variables

Reference variables using Jinja2A templating engine for Python that Ansible uses for variable substitution, conditionals, loops, and filters. syntax with double curly braces:

Variable reference syntax
tasks:
  # Simple variable
  - name: Create document root
    ansible.builtin.file:
      path: "{{ doc_root }}"
      state: directory

  # Dictionary access
  - name: Display config
    ansible.builtin.debug:
      msg: "Max clients: {{ server_config.max_clients }}"

  # List access
  - name: Display first package
    ansible.builtin.debug:
      msg: "First: {{ packages[0] }}"
⚠️ Important: Quoting Variables

When a value starts with a variable reference, you must quote the entire value:

# Wrong - YAML syntax error
path: {{ doc_root }}/html

# Correct - quoted
path: "{{ doc_root }}/html"

Registered Variables

Capture task output using register:

Using register
tasks:
  - name: Check service status
    ansible.builtin.command:
      cmd: systemctl is-active httpd
    register: httpd_status
    ignore_errors: true
    changed_when: false

  - name: Display status
    ansible.builtin.debug:
      msg: "httpd is {{ httpd_status.stdout }}"

  - name: Start if not running
    ansible.builtin.service:
      name: httpd
      state: started
    when: httpd_status.rc != 0

Common Registered Variable Attributes

AttributeDescription
changedBoolean - if task made changes
failedBoolean - if task failed
rcReturn code (command/shell)
stdoutStandard output
stderrStandard error
stdout_linesOutput as list of lines

Handlers

Handlers are special tasks that only run when notified by other tasks.

What are Handlers?

HandlersSpecial tasks that only execute when notified. Run once at end of play, regardless of how many times notified. Perfect for service restarts. respond to notifications from tasks. Key characteristics:

🔔
Notification Triggered
Only run when notified by a task that reports "changed"
1️⃣
Run Once
Each handler runs only once, even if notified multiple times
⏰
End of Play
Execute at the end of the play, after all tasks complete

Basic Handler Syntax

Handler example
---
- name: Configure web server
  hosts: webservers
  become: true

  tasks:
    - name: Install httpd
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Copy httpd configuration
      ansible.builtin.copy:
        src: files/httpd.conf
        dest: /etc/httpd/conf/httpd.conf
      notify: Restart httpd

    - name: Copy SSL configuration
      ansible.builtin.copy:
        src: files/ssl.conf
        dest: /etc/httpd/conf.d/ssl.conf
      notify: Restart httpd

  handlers:
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Handler Execution Flow

When Do Handlers Run?
✓ Task 1: Install httpd
STATUS: ok (no change)
↓
✓ Task 2: Copy httpd.conf
STATUS: changed → notify
↓
✓ Task 3: Copy ssl.conf
STATUS: changed → notify
↓ All tasks complete
🔔 Handler: Restart httpd
RUNS ONCE (despite 2 notifications)

Multiple Handlers

Notifying multiple handlers
tasks:
  - name: Update app configuration
    ansible.builtin.template:
      src: app.conf.j2
      dest: /etc/myapp/app.conf
    notify:
      - Restart application
      - Clear application cache

handlers:
  - name: Restart application
    ansible.builtin.service:
      name: myapp
      state: restarted

  - name: Clear application cache
    ansible.builtin.file:
      path: /var/cache/myapp
      state: absent

Flushing Handlers

Force handlers to run mid-play with meta: flush_handlers:

Flush handlers
tasks:
  - name: Update configuration
    ansible.builtin.template:
      src: httpd.conf.j2
      dest: /etc/httpd/conf/httpd.conf
    notify: Restart httpd

  - name: Force handlers now
    ansible.builtin.meta: flush_handlers

  - name: Verify service
    ansible.builtin.uri:
      url: http://localhost/
      status_code: 200
💡 Best Practice

Use handlers for operations that should only happen when configuration changes, like service restarts. This prevents unnecessary service disruptions.

Running Playbooks

Execute playbooks using ansible-playbook and ansible-navigator commands.

The ansible-playbook Command

Basic usage
# Basic execution
$ ansible-playbook playbook.yml

# Specify inventory
$ ansible-playbook -i inventory/production playbook.yml

# Verbose output
$ ansible-playbook -v playbook.yml
$ ansible-playbook -vvv playbook.yml

# Limit to specific hosts
$ ansible-playbook playbook.yml --limit webservers

# Pass extra variables
$ ansible-playbook playbook.yml -e "env=production"

# Ask for become password
$ ansible-playbook playbook.yml --ask-become-pass

Common Options

OptionDescription
-i INVENTORYSpecify inventory file
-e VARSSet additional variables
--limit SUBSETLimit to specific hosts
-v, -vv, -vvvIncrease verbosity
--checkDry run (no changes)
--diffShow file differences
--syntax-checkCheck syntax only
--list-tasksList tasks without running
--list-hostsList targeted hosts
--tags TAGSOnly run tagged tasks
--skip-tags TAGSSkip tagged tasks

Validation and Dry Runs

Test your playbooks before execution to catch errors early.

Syntax Check

Use --syntax-check to validate playbook syntax:

Syntax check
# Check syntax
$ ansible-playbook --syntax-check playbook.yml

# Success output
playbook: playbook.yml

# Error output example
ERROR! Syntax Error while loading YAML.
  mapping values are not allowed in this context
The error appears to be in 'playbook.yml': line 10, column 12

Common Syntax Errors

🔴 Indentation Errors ▼

The most common error. YAML requires consistent spaces (not tabs).

Solution: Check indentation, use 2 spaces per level, never use tabs.

🔴 Missing Quotes ▼

Values with special characters need quotes.

Solution: Quote values starting with {{ or containing colons.

🔴 Invalid Module Names ▼

Typos in module names or non-existent modules.

Solution: Check spelling. Use ansible-doc -l to list modules.

Check Mode (Dry Run)

Check modeExecutes the playbook without making changes, showing what would change if run normally. shows what would happen without making changes:

Check mode
# Dry run
$ ansible-playbook playbook.yml --check

# Dry run with diff
$ ansible-playbook playbook.yml --check --diff
⚠️ Check Mode Limitations

Not all modules support check mode. Modules like command and shell cannot predict changes.

Using ansible-lint

ansible-lintA tool that checks playbooks for best practices beyond syntax checking. enforces best practices:

ansible-lint
# Install
$ pip install ansible-lint

# Run lint
$ ansible-lint playbook.yml

# Example output
WARNING Listing 2 violation(s) that are fatal
name[missing]: All tasks should be named.
fqcn[action-core]: Use FQCN for builtin modules.

Hands-On Lab

Build a complete playbook to configure a web server.

Lab Exercise Configure a Web Server with Ansible

Create a playbook that performs the following:

  • Install Apache HTTP Server (httpd)
  • Create a custom index.html page
  • Start and enable the httpd service
  • Configure firewall for HTTP traffic
  • Use handlers to restart on config changes

Create playbook structure

---
- name: Configure web server
  hosts: webservers
  become: true

  vars:
    http_port: 80
    doc_root: /var/www/html

  tasks:
    # Tasks go here

  handlers:
    # Handlers go here

Add package installation

  tasks:
    - name: Install packages
      ansible.builtin.dnf:
        name:
          - httpd
          - firewalld
        state: present

Add service management

    - name: Start and enable httpd
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

Add content deployment

    - name: Create index.html
      ansible.builtin.copy:
        content: |
          <h1>Managed by Ansible</h1>
          <p>Server: {{ ansible_hostname }}</p>
        dest: "{{ doc_root }}/index.html"
        mode: '0644'

Configure firewall

    - name: Start firewalld
      ansible.builtin.service:
        name: firewalld
        state: started
        enabled: true

    - name: Allow HTTP
      ansible.posix.firewalld:
        service: http
        permanent: true
        state: enabled
        immediate: true

Add handler

  handlers:
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Test and run

# Check syntax
$ ansible-playbook webserver.yml --syntax-check

# Dry run
$ ansible-playbook webserver.yml --check --diff

# Run
$ ansible-playbook webserver.yml
