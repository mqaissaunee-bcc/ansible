What is a Playbook?

Playbooks are Ansible's configuration, deployment, and orchestration language, expressed in YAML format.

Ad-hoc Commands vs. Playbooks

While ad-hoc commandsSingle-line Ansible commands executed from the CLI. Useful for quick tasks but not reusable. are useful for quick tasks, playbooksYAML files containing plays that define automation tasks. Reusable, version-controllable, and can express complex workflows. provide power and flexibility.

FeatureAd-hoc CommandsPlaybooks
ReusabilityNot easily reusableHighly reusable
Version ControlDifficult to trackEasy with Git
ComplexitySingle tasks onlyMulti-step workflows
VariablesLimited supportFull variable support
Conditionals/LoopsNot supportedFull logic support

YAML Syntax

YAML (YAML Ain't Markup Language) is a human-readable data format used for Ansible playbooks.

YAML Basics

📏
Indentation
Use spaces only (never tabs). Standard is 2 spaces per level.
🔑
Key-Value Pairs
Format: key: value with a space after the colon.
📋
Lists
Items start with a dash and space: - item

Data Types

YAML data types 
# Strings
name: Configure webserver
quoted: "String with: special chars"

# Numbers
port: 80
timeout: 30.5

# Booleans
enabled: true
debug: false

# Lists
packages:
  - httpd
  - firewalld

# Dictionaries
server:
  hostname: web1
  ip: 192.168.1.10
⚠️ Common Mistakes

Tabs: Never use tabs - YAML requires spaces.
Colons: Values with colons need quotes: "http://example.com"
Variables: Values starting with {{ must be quoted.

Building an Ansible Inventory

The inventory defines which hosts Ansible manages and how they are organized into groups.

What is an Inventory?

An inventoryA file or directory that defines the managed hosts and groups that Ansible can target. Can be static (INI/YAML files) or dynamic (scripts/plugins). is a list of managed hosts that Ansible can target. It organizes hosts into groups for easier management and allows you to define variables for hosts and groups.

📄
Static Inventory
Text files in INI or YAML format listing hosts and groups manually.
🔄
Dynamic Inventory
Scripts or plugins that generate inventory from external sources (cloud, CMDB).

INI Format Inventory

The most common inventory format uses INI-style syntax:

inventory/hosts (INI format) 
# Individual hosts (ungrouped)
server1.example.com
192.168.1.100

# Host group: webservers
[webservers]
web1.example.com
web2.example.com
web3.example.com

# Host group: dbservers
[dbservers]
db1.example.com
db2.example.com

# Group of groups (children)
[production:children]
webservers
dbservers

# Group variables
[webservers:vars]
http_port=80
ansible_user=admin

# Host with specific variables
[dbservers]
db1.example.com ansible_port=2222
db2.example.com ansible_host=192.168.1.50

YAML Format Inventory

inventory/hosts.yml (YAML format) 
all:
  children:
    webservers:
      hosts:
        web1.example.com:
        web2.example.com:
      vars:
        http_port: 80
    dbservers:
      hosts:
        db1.example.com:
          ansible_port: 2222
        db2.example.com:
    production:
      children:
        webservers:
        dbservers:

Host Ranges and Patterns

Using ranges in inventory 
# Numeric range
[webservers]
web[1:5].example.com     # web1, web2, web3, web4, web5

# Alphabetic range
[dbservers]
db-[a:c].example.com     # db-a, db-b, db-c

# Zero-padded numbers
[servers]
server[01:10].example.com # server01, server02, ... server10

Verifying Inventory

Useful inventory commands 
# List all hosts in inventory
$ ansible all --list-hosts -i inventory/hosts

# List hosts in a specific group
$ ansible webservers --list-hosts -i inventory/hosts

# Show inventory in graph format
$ ansible-inventory --graph -i inventory/hosts

# Show all inventory variables for a host
$ ansible-inventory --host web1.example.com -i inventory/hosts

Special Groups

GroupDescription
allContains every host in the inventory
ungroupedHosts not in any other group (except all)
💡 Best Practice

Organize inventory into directories with separate files for hosts, group_vars, and host_vars for better maintainability in large environments.

Managing Ansible Configuration Files

The ansible.cfg file controls Ansible's behavior, including default settings for inventory, connections, and privilege escalation.

Configuration File Precedence

Ansible searches for configuration files in this order (first found wins):

Configuration File Search Order
HIGHEST PRIORITY
$ANSIBLE_CONFIG env variable
↓
CURRENT DIRECTORY
./ansible.cfg
↓
HOME DIRECTORY
~/.ansible.cfg
↓
LOWEST PRIORITY
/etc/ansible/ansible.cfg
💡 Best Practice

Create a project-specific ansible.cfg in your project directory. This ensures consistent behavior and allows version control of your configuration.

Configuration File Structure

The ansible.cfg file uses INI format with sections denoted by [section] headers:

ansible.cfg - Complete Example 
[defaults]
# Inventory location
inventory = ./inventory

# Remote user for SSH connections
remote_user = devops

# Disable host key checking (lab environments only)
host_key_checking = False

# Number of parallel connections
forks = 5

# Default module to use with ansible command
module_name = command

# Retry files location (or disable)
retry_files_enabled = False

# Roles path
roles_path = ./roles:/usr/share/ansible/roles

[privilege_escalation]
# Enable privilege escalation by default
become = True
become_method = sudo
become_user = root
become_ask_pass = False

[ssh_connection]
# SSH-specific settings
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=60s

Key Configuration Options

[defaults] Section

OptionDescriptionExample
inventoryPath to inventory file/directory./inventory
remote_userDefault SSH useransible
host_key_checkingCheck SSH host keysFalse
forksParallel processes5
timeoutSSH connection timeout10
log_pathLog file location./ansible.log

[privilege_escalation] Section

OptionDescriptionDefault
becomeEnable privilege escalationFalse
become_methodEscalation methodsudo
become_userUser to becomeroot
become_ask_passPrompt for passwordFalse

Viewing Current Configuration

Configuration commands 
# Show which config file is being used
$ ansible --version
ansible [core 2.14.0]
  config file = /home/student/project/ansible.cfg
  ...

# View all configuration settings
$ ansible-config view

# List all settings with their origins
$ ansible-config list

# Dump current configuration
$ ansible-config dump

# Show only non-default settings
$ ansible-config dump --only-changed

Environment Variables

Configuration can also be set via environment variables:

Environment variable examples 
# Override config file location
$ export ANSIBLE_CONFIG=/path/to/ansible.cfg

# Set inventory
$ export ANSIBLE_INVENTORY=/path/to/inventory

# Set remote user
$ export ANSIBLE_REMOTE_USER=admin

# Enable verbose mode
$ export ANSIBLE_VERBOSITY=2
⚠️ Security Note

Never set host_key_checking = False in production environments. This disables SSH host key verification and opens potential man-in-the-middle attack vectors.

Playbook Structure

Understanding playbook anatomy is essential for writing effective automation.

Complete Playbook Example

webserver.yml 
---
- name: Configure web servers       # Play name
  hosts: webservers                   # Target hosts (REQUIRED)
  become: true                        # Privilege escalation

  vars:                                # Play variables
    http_port: 80
    doc_root: /var/www/html

  tasks:                               # Task list
    - name: Install Apache            # Task name
      ansible.builtin.dnf:             # Module (FQCN)
        name: httpd                    # Module parameter
        state: present                 # Module parameter

    - name: Start httpd service
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

  handlers:                            # Handler list
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Play Attributes

AttributeRequiredDescription
nameRecommendedDescriptive name for the play
hostsYesTarget hosts/groups from inventory
becomeNoEnable privilege escalation
varsNoDefine variables for the play
tasksNo*List of tasks to execute
handlersNoTasks triggered by notifications
gather_factsNoCollect host facts (default: true)

Host Patterns

Common host patterns
hosts: all                      # All hosts
hosts: webservers               # Single group
hosts: webservers:dbservers     # Multiple groups (OR)
hosts: webservers:&staging      # Intersection (AND)
hosts: webservers:!testing      # Exclude group
hosts: web1.example.com        # Single host
hosts: *.example.com           # Wildcard

Working with Modules

Modules are the building blocks of Ansible tasks.

Fully Qualified Collection Names (FQCNs)

Always use FQCNsFully Qualified Collection Name - the complete path to a module: namespace.collection.module:

# Recommended: FQCN
ansible.builtin.copy:
  src: file.txt
  dest: /tmp/file.txt

# Not recommended: short name
copy:
  src: file.txt

Essential Modules

ansible.builtin.copy
Copy files from control node to managed hosts.
- name: Copy config file
  ansible.builtin.copy:
    src: files/httpd.conf
    dest: /etc/httpd/conf/httpd.conf
    owner: root
    mode: '0644'
ansible.builtin.file
Manage file and directory properties.
- name: Create directory
  ansible.builtin.file:
    path: /var/www/html
    state: directory
    mode: '0755'
ansible.builtin.dnf
Manage packages with DNF (RHEL 8+).
- name: Install packages
  ansible.builtin.dnf:
    name:
      - httpd
      - firewalld
    state: present
ansible.builtin.service
Manage services.
- name: Start httpd
  ansible.builtin.service:
    name: httpd
    state: started
    enabled: true
ansible.posix.firewalld
Manage firewalld rules.
- name: Allow HTTP
  ansible.posix.firewalld:
    service: http
    permanent: true
    state: enabled
    immediate: true
ansible.builtin.command
Execute commands (no shell features).
- name: Run command
  ansible.builtin.command:
    cmd: /usr/bin/myapp --init
    creates: /opt/myapp/.initialized
ansible.builtin.debug
Print debug messages.
- name: Display variable
  ansible.builtin.debug:
    msg: "Port is {{ http_port }}"

Variables in Playbooks

Variables make playbooks flexible and reusable.

Defining Variables

Play-Level Variables

Variables in play
---
- name: Configure web server
  hosts: webservers
  vars:
    http_port: 80
    doc_root: /var/www/html
    packages:
      - httpd
      - mod_ssl

  tasks:
    - name: Install packages
      ansible.builtin.dnf:
        name: "{{ packages }}"
        state: present

External Variable Files

Using vars_files
---
- name: Configure web server
  hosts: webservers
  vars_files:
    - vars/webserver.yml
  tasks:
    - name: Display port
      ansible.builtin.debug:
        msg: "Port: {{ http_port }}"

Command Line Variables

# Pass variable at runtime
$ ansible-playbook site.yml -e "http_port=8080"

# Multiple variables
$ ansible-playbook site.yml -e "http_port=8080 env=production"

# From file
$ ansible-playbook site.yml -e @vars/production.yml
⚠️ Quoting Variables

When a value starts with {{, you must quote the entire value:

# Wrong
path: {{ doc_root }}/html

# Correct
path: "{{ doc_root }}/html"

Handlers

Handlers are special tasks that only run when notified.

🔔
Notification Triggered
Only run when notified by a task that reports "changed"
1️⃣
Run Once
Each handler runs only once, even if notified multiple times
⏰
End of Play
Execute at the end of the play, after all tasks

Handler Example

Using handlers
---
- name: Configure web server
  hosts: webservers
  become: true

  tasks:
    - name: Copy httpd configuration
      ansible.builtin.copy:
        src: files/httpd.conf
        dest: /etc/httpd/conf/httpd.conf
      notify: Restart httpd   # Notify handler

    - name: Copy SSL configuration
      ansible.builtin.copy:
        src: files/ssl.conf
        dest: /etc/httpd/conf.d/ssl.conf
      notify: Restart httpd   # Same handler

  handlers:
    - name: Restart httpd        # Runs ONCE at end
      ansible.builtin.service:
        name: httpd
        state: restarted

Running Playbooks

Execute playbooks using ansible-playbook and ansible-navigator.

The ansible-playbook Command

Basic usage
# Basic execution
$ ansible-playbook playbook.yml

# Specify inventory
$ ansible-playbook -i inventory playbook.yml

# Verbose output
$ ansible-playbook -v playbook.yml
$ ansible-playbook -vvv playbook.yml

# Limit to specific hosts
$ ansible-playbook playbook.yml --limit webservers

# Pass extra variables
$ ansible-playbook playbook.yml -e "env=production"

Common Options

OptionDescription
-i INVENTORYSpecify inventory
-e VARSExtra variables
--limit HOSTLimit to hosts
-v, -vv, -vvvVerbosity level
--checkDry run
--diffShow file changes
--syntax-checkCheck syntax only
--list-tasksList tasks
--list-hostsList target hosts

Implementing Multiple Plays

A playbook can contain multiple plays, each targeting different hosts with different tasks.

Why Multiple Plays?

Multiple plays allow you to organize complex automation workflows where different tasks need to run on different hosts or with different privileges.

🎯
Target Different Hosts
Configure web servers in one play, database servers in another.
🔐
Different Privileges
Some plays may need become: true, others run as regular user.
📊
Logical Separation
Organize related tasks together for better readability.

Multiple Plays Structure

Each play in a playbook starts with a dash (-) at the root level of the YAML list:

site.yml - Multiple Plays Example 
---
# Play 1: Configure Web Servers
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    - name: Install httpd
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Start httpd service
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

    - name: Open firewall for HTTP
      ansible.posix.firewalld:
        service: http
        permanent: true
        state: enabled
        immediate: true

# Play 2: Configure Database Servers
- name: Configure database servers
  hosts: dbservers
  become: true

  tasks:
    - name: Install MariaDB
      ansible.builtin.dnf:
        name:
          - mariadb-server
          - python3-PyMySQL
        state: present

    - name: Start MariaDB service
      ansible.builtin.service:
        name: mariadb
        state: started
        enabled: true

# Play 3: Verify All Servers
- name: Verify deployment
  hosts: all
  gather_facts: false

  tasks:
    - name: Print completion message
      ansible.builtin.debug:
        msg: "Configuration complete on {{ inventory_hostname }}"

Play Execution Order

Multiple Plays Execution Flow
PLAY 1
Configure web servers
↓ Runs on: webservers group
PLAY 2
Configure database servers
↓ Runs on: dbservers group
PLAY 3
Verify deployment
↓ Runs on: all hosts
COMPLETE
Playbook Finished

Use Cases for Multiple Plays

1. Staged Deployment

staged-deploy.yml
---
# Deploy to staging first
- name: Deploy to staging
  hosts: staging
  tasks:
    - name: Deploy application
      ansible.builtin.include_tasks: tasks/deploy.yml

# Then deploy to production
- name: Deploy to production
  hosts: production
  tasks:
    - name: Deploy application
      ansible.builtin.include_tasks: tasks/deploy.yml

2. Different Privilege Levels

mixed-privileges.yml
---
# System tasks requiring root
- name: Configure system
  hosts: webservers
  become: true
  tasks:
    - name: Install packages
      ansible.builtin.dnf:
        name: httpd
        state: present

# Application tasks as app user
- name: Deploy application
  hosts: webservers
  become: true
  become_user: appuser
  tasks:
    - name: Deploy app code
      ansible.builtin.git:
        repo: https://github.com/example/app.git
        dest: /opt/app

3. Multi-Tier Architecture

three-tier.yml
---
# Configure load balancers
- name: Configure load balancers
  hosts: loadbalancers
  roles:
    - haproxy

# Configure web tier
- name: Configure web servers
  hosts: webservers
  roles:
    - apache
    - php

# Configure database tier
- name: Configure database servers
  hosts: dbservers
  roles:
    - mariadb
💡 Best Practice

Give each play a descriptive name. This makes output easier to read and helps identify which play is running during execution.

⚠️ Important

Variables defined with vars: in one play are not available in other plays. Use vars_files: or inventory variables for values that need to be shared across plays.

Validation and Dry Runs

Test playbooks before execution to catch errors early.

Syntax Check

Syntax validation
# Check syntax only
$ ansible-playbook --syntax-check playbook.yml

# Success output
playbook: playbook.yml

# Error output
ERROR! Syntax Error while loading YAML.
  mapping values are not allowed in this context
The error appears to be in 'playbook.yml': line 10

Check Mode (Dry Run)

Run without making changes to see what would happen:

Dry run commands
# Dry run
$ ansible-playbook playbook.yml --check

# Dry run with diff (show changes)
$ ansible-playbook playbook.yml --check --diff

# List tasks without running
$ ansible-playbook playbook.yml --list-tasks

# List target hosts
$ ansible-playbook playbook.yml --list-hosts
⚠️ Check Mode Limitations

Not all modules support check mode. The command and shell modules cannot predict what would change.

Using ansible-lint

# Install ansible-lint
$ pip install ansible-lint

# Run lint checks
$ ansible-lint playbook.yml

# Example output
WARNING Listing 2 violation(s) that are fatal
name[missing]: All tasks should be named.
fqcn[action-core]: Use FQCN for builtin modules.
