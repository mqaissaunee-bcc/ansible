Variable Fundamentals

Variables in Ansible store values that can be reused throughout your playbooks, making automation flexible and maintainable.

Why Use Variables?

🔄
Reusability
Write playbooks once and use them across different environments by changing variable values.
🔧
Maintainability
Change values in one place instead of searching through multiple playbooks.
🔒
Security
Separate sensitive data from playbook code and use Ansible Vault for encryption.

Variable Naming Rules

📝 Naming Requirements
  • Must start with a letter (a-z, A-Z)
  • Can contain letters, numbers, and underscores only
  • Cannot contain spaces, hyphens, or special characters
  • Case-sensitive (MyVar ≠ myvar)
Valid and Invalid Variable Names
# Valid variable names
http_port: 80
maxRetries: 3
server_name_1: web01

# Invalid - DO NOT USE
# 1server: value       # Cannot start with number
# server-name: value   # Cannot contain hyphens
# my var: value        # Cannot contain spaces

Defining Variables in Playbooks

play-vars.yml
---
- name: Configure web server
  hosts: webservers
  become: true
  
  vars:
    http_port: 80
    https_port: 443
    doc_root: /var/www/html
    packages:
      - httpd
      - mod_ssl

  tasks:
    - name: Install web packages
      ansible.builtin.dnf:
        name: "{{ packages }}"
        state: present

Variable Data Types

vars:
  server_name: webserver01
  message: "Welcome to {{ server_name }}"
  banner: |
    Welcome to the server.
    Unauthorized access prohibited.
vars:
  http_port: 80
  max_connections: 1000
  timeout: 30.5
  file_mode: '0755'  # Quote to preserve
vars:
  packages:
    - httpd
    - mod_ssl
    - php
  ports: [80, 443, 8080]
  # Access: {{ packages[0] }} → httpd
vars:
  server_config:
    hostname: web01.example.com
    ip_address: 192.168.1.10
    port: 80
  # Access: {{ server_config.hostname }}
  # Or: {{ server_config['ip_address'] }}

Using Variables with Jinja2A templating engine for Python that Ansible uses for variable substitution, conditionals, loops, and filters.

Variable Reference Syntax
tasks:
  - name: Display the HTTP port
    ansible.builtin.debug:
      msg: "HTTP port is {{ http_port }}"

  - name: Create document root
    ansible.builtin.file:
      path: "{{ doc_root }}"
      state: directory
⚠️ Important: Quoting Variables

When a value starts with a variable reference, you must quote the entire value:

# Wrong - YAML syntax error
path: {{ doc_root }}/html

# Correct - quoted
path: "{{ doc_root }}/html"

Variable Scope

Understanding where variables can be defined helps you organize your automation effectively and avoid conflicts.

Variable Scope Levels

Variables in Ansible exist at different scope levelsThe context in which a variable is accessible. Variables defined at a broader scope are available to all narrower scopes.:

Variable Scope Hierarchy
1
Global Scope — Extra vars (-e), set_fact, include_vars
2
Play Scope — Play vars, vars_files, vars_prompt
3
Host Scope — host_vars, inventory host variables
4
Group Scope — group_vars, inventory group variables

Where to Define Variables

1. Inventory Variables

inventory/hosts
# Host variables - specific to a single host
[webservers]
web1.example.com http_port=80
web2.example.com http_port=8080

# Group variables - shared by all hosts
[webservers:vars]
doc_root=/var/www/html
max_clients=256

2. Play Variables (vars)

playbook.yml
---
- name: Configure application
  hosts: webservers
  
  vars:
    app_name: mywebapp
    app_version: "2.1.0"
    env: production

  tasks:
    - name: Display app info
      ansible.builtin.debug:
        msg: "Deploying {{ app_name }} v{{ app_version }}"

3. External Variable Files (vars_files)

vars/webserver.yml
---
http_port: 80
https_port: 443
doc_root: /var/www/html
Playbook using vars_files
---
- name: Configure web server
  hosts: webservers
  
  vars_files:
    - vars/webserver.yml

  tasks:
    - name: Show configuration
      ansible.builtin.debug:
        msg: "HTTP: {{ http_port }}"

4. Command Line Variables (-e)

Command line variable examples
# Single variable
$ ansible-playbook site.yml -e "env=staging"

# Multiple variables
$ ansible-playbook site.yml -e "env=staging http_port=8080"

# Variables from file
$ ansible-playbook site.yml -e @vars/staging.yml

5. Registered Variables

Using register to capture output
tasks:
  - name: Check service status
    ansible.builtin.command:
      cmd: systemctl is-active httpd
    register: httpd_status
    ignore_errors: true
    changed_when: false

  - name: Start httpd if not running
    ansible.builtin.service:
      name: httpd
      state: started
    when: httpd_status.rc != 0

Registered Variable Attributes

AttributeDescription
rcReturn code (0 = success)
stdoutStandard output as string
stdout_linesStandard output as list of lines
stderrStandard error as string
changedWhether task made changes (boolean)
failedWhether task failed (boolean)

Variable Precedence

When the same variable is defined in multiple places, Ansible uses a specific precedence order to determine which value to use.

Understanding Precedence

Ansible has 22 levels of variable precedence. Variables defined at higher precedence levels override those at lower levels.

Variable Precedence (Highest to Lowest)
1
Extra vars (-e command line)
2
Task vars (only for the task)
3
Block vars (only for tasks in block)
4
Play vars_files
5
Play vars
6
host_vars (file)
7
Inventory host vars
8
group_vars (file)
9
Inventory group vars
10
Role defaults

High Always wins Medium Common overrides Low Base values

💡 Best Practices
  • Use role defaults for base values — Easy to override
  • Use group_vars for environment settings — Apply to multiple hosts
  • Use host_vars for host-specific overrides — One host, one config
  • Reserve extra vars for runtime overrides — Testing and emergencies

Managing Variable Files

Organize variables using host_vars and group_vars directories for clean, maintainable automation.

Directory Structure

Recommended Project Structure
project/
├── ansible.cfg
├── inventory/
│   ├── hosts                 # Inventory file
│   ├── group_vars/
│   │   ├── all.yml          # Variables for all hosts
│   │   ├── webservers.yml   # Variables for webservers
│   │   └── dbservers.yml    # Variables for dbservers
│   └── host_vars/
│       ├── web1.example.com.yml
│       └── db1.example.com.yml
├── playbooks/
│   └── site.yml
└── roles/

The group_varsA directory containing YAML files named after inventory groups. Variables defined here apply to all hosts in the corresponding group. Directory

group_vars/all.yml
---
# Variables for ALL hosts
ntp_server: time.example.com
dns_servers:
  - 8.8.8.8
  - 8.8.4.4
timezone: America/New_York
group_vars/webservers.yml
---
# Variables for webservers group only
http_port: 80
https_port: 443
doc_root: /var/www/html
packages:
  - httpd
  - mod_ssl

The host_varsA directory containing YAML files named after specific hosts. Variables defined here apply only to that particular host and override group variables. Directory

host_vars/web1.example.com.yml
---
# Variables specific to this host
http_port: 8080         # Override from group_vars
ssl_cert: /etc/pki/tls/certs/web1.crt
ssl_key: /etc/pki/tls/private/web1.key

Dynamic Variable Loading with include_vars

Using include_vars
tasks:
  # Load based on environment
  - name: Load environment-specific variables
    ansible.builtin.include_vars:
      file: "vars/{{ env }}.yml"

  # Load based on OS family
  - name: Load OS-specific variables
    ansible.builtin.include_vars:
      file: "vars/{{ ansible_facts['os_family'] }}.yml"

Understanding Ansible Facts

Facts are system information automatically discovered by Ansible when it connects to managed hosts.

What Are Ansible FactsVariables automatically discovered and set by Ansible when connecting to managed hosts. They contain system information like IP addresses, OS version, and hardware details.?

🖥️
System Info
Operating system, kernel version, architecture, hostname, and domain.
🌐
Network Info
IP addresses, MAC addresses, interfaces, and DNS configuration.
💾
Hardware Info
CPU count, memory size, disk devices, and virtualization details.

Viewing Facts

Gathering facts from command line
# View all facts for a host
$ ansible web1.example.com -m ansible.builtin.setup

# Filter specific facts
$ ansible web1.example.com -m ansible.builtin.setup -a "filter=ansible_distribution*"

# View network-related facts
$ ansible web1.example.com -m ansible.builtin.setup -a "filter=ansible_*_ipv4"

Fact Explorer

🔍 Interactive Fact Browser
ansible_facts
distribution
ansible_distribution: "RedHat"
ansible_distribution_version: "9.2"
ansible_os_family: "RedHat"
network
ansible_hostname: "web1"
ansible_fqdn: "web1.example.com"
ansible_default_ipv4.address: "192.168.1.10"
hardware
ansible_processor_vcpus: 4
ansible_memtotal_mb: 8192
ansible_architecture: "x86_64"

Using Facts in Playbooks

Referencing facts in playbooks
tasks:
  # Using ansible_facts dictionary (recommended)
  - name: Display OS information
    ansible.builtin.debug:
      msg: "OS: {{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }}"

  # Conditional based on facts
  - name: Install on Red Hat systems only
    ansible.builtin.dnf:
      name: httpd
      state: present
    when: ansible_facts['os_family'] == "RedHat"

  # Using network facts
  - name: Configure based on IP
    ansible.builtin.template:
      src: config.j2
      dest: /etc/app/config.conf
    vars:
      server_ip: "{{ ansible_facts['default_ipv4']['address'] }}"

Controlling Fact Gathering

Fact gathering options
# Disable fact gathering (faster execution)
- name: Quick task without facts
  hosts: all
  gather_facts: false
  tasks:
    - name: Run a command
      ansible.builtin.command:
        cmd: uptime

# Gather facts explicitly when needed
- name: Gather facts manually
  hosts: all
  gather_facts: false
  tasks:
    - name: Now gather facts
      ansible.builtin.setup:
⚠️ Performance Note

Fact gathering takes time, especially with many hosts. If you don't need facts, disable gathering with gather_facts: false to speed up playbook execution.

Custom Facts

Create your own facts on managed hosts to provide application-specific or organizational data.

What Are Custom FactsUser-defined facts stored on managed hosts in the /etc/ansible/facts.d/ directory. These are gathered automatically alongside system facts.?

Custom facts (also called local facts) are facts you define on managed hosts. They are stored in /etc/ansible/facts.d/.

Creating Custom Facts

/etc/ansible/facts.d/custom.fact
[application]
name = mywebapp
version = 2.1.0
environment = production

[deployment]
last_deploy = 2024-01-15
deployed_by = admin
/etc/ansible/facts.d/custom.fact
{
  "application": {
    "name": "mywebapp",
    "version": "2.1.0",
    "environment": "production"
  },
  "deployment": {
    "last_deploy": "2024-01-15",
    "deployed_by": "admin"
  }
}
/etc/ansible/facts.d/dynamic.fact (executable)
#!/bin/bash
# Dynamic fact script - must output JSON
APP_VERSION=$(myapp --version 2>/dev/null || echo "unknown")
CONNECTIONS=$(ss -tun | wc -l)

cat <<EOF
{
  "runtime": {
    "app_version": "$APP_VERSION",
    "active_connections": $CONNECTIONS
  }
}
EOF

Deploying Custom Facts

deploy-facts.yml
---
- name: Deploy custom facts
  hosts: all
  become: true

  tasks:
    - name: Create facts directory
      ansible.builtin.file:
        path: /etc/ansible/facts.d
        state: directory
        mode: '0755'

    - name: Deploy application fact
      ansible.builtin.copy:
        content: |
          [application]
          name = mywebapp
          version = 2.1.0
        dest: /etc/ansible/facts.d/app.fact
        mode: '0644'

    - name: Re-gather facts
      ansible.builtin.setup:
        filter: ansible_local

    - name: Display custom facts
      ansible.builtin.debug:
        var: ansible_local

Accessing Custom Facts

Using custom facts
tasks:
  # Access INI-style facts
  - name: Show application name
    ansible.builtin.debug:
      msg: "App: {{ ansible_local.app.application.name }}"

  # Use in conditionals
  - name: Production-only task
    ansible.builtin.debug:
      msg: "Running in production!"
    when: ansible_local.app.application.environment == 'production'
💡 Use Cases for Custom Facts
  • Track application versions across servers
  • Store deployment metadata
  • Define server roles or tiers
  • Capture dynamic runtime information

Magic Variables

Special variables automatically set by Ansible that provide information about hosts, groups, and execution context.

What Are Magic VariablesReserved variable names that Ansible sets automatically. They cannot be directly overwritten and provide access to inventory data and execution context.?

VariableDescription
hostvarsDictionary of all hosts' variables, keyed by hostname
groupsDictionary of all groups and their member hosts
group_namesList of groups the current host belongs to
inventory_hostnameName of the current host as in the inventory
inventory_hostname_shortShort version of the hostname (first part)
ansible_play_hostsList of active hosts in the current play

Using hostvars

Accessing other hosts' variables
tasks:
  # Get a fact from another host
  - name: Display database server IP
    ansible.builtin.debug:
      msg: "DB IP: {{ hostvars['db1.example.com']['ansible_default_ipv4']['address'] }}"

  # Configure app to connect to database
  - name: Create database configuration
    ansible.builtin.template:
      src: db_config.j2
      dest: /etc/app/database.conf
    vars:
      db_host: "{{ hostvars['db1.example.com']['ansible_fqdn'] }}"

Using groups

Working with groups variable
tasks:
  # List all hosts in a group
  - name: Show all web servers
    ansible.builtin.debug:
      msg: "Web servers: {{ groups['webservers'] }}"

  # Run only on load balancers
  - name: Create HAProxy config
    ansible.builtin.template:
      src: haproxy.cfg.j2
      dest: /etc/haproxy/haproxy.cfg
    when: "'loadbalancers' in group_names"

Using inventory_hostname

Using inventory_hostname
tasks:
  - name: Display current host
    ansible.builtin.debug:
      msg: "Running on: {{ inventory_hostname }}"

  - name: Set hostname to match inventory
    ansible.builtin.hostname:
      name: "{{ inventory_hostname_short }}"

  - name: Create host-specific log directory
    ansible.builtin.file:
      path: "/var/log/app/{{ inventory_hostname }}"
      state: directory

Using group_names

Conditional execution based on group
tasks:
  - name: Show groups for this host
    ansible.builtin.debug:
      msg: "Member of: {{ group_names }}"

  - name: Install web server packages
    ansible.builtin.dnf:
      name: httpd
      state: present
    when: "'webservers' in group_names"

  - name: Install database packages
    ansible.builtin.dnf:
      name: mysql-server
      state: present
    when: "'dbservers' in group_names"
⚠️ Important: Facts Must Be Gathered First

When accessing another host's facts via hostvars, those facts must have been gathered first. Either run a play against those hosts first, or use delegate_to.
