The when Clause

Conditionals allow you to control whether a task runs based on variables, facts, or registered results.

Understanding Conditionals

The whenA task attribute that evaluates a Jinja2 expression. The task runs only if the expression evaluates to true. clause is used to conditionally execute tasks. Ansible evaluates the condition before running the task, and skips it if the condition is false.

💡 Key Point

The when clause uses raw Jinja2 expressions without the double curly braces {{ }}. Variables are referenced by name directly.

Basic when Syntax

Simple conditional example
tasks:
  - name: Install httpd on Red Hat systems
    ansible.builtin.dnf:
      name: httpd
      state: present
    when: ansible_facts['os_family'] == "RedHat"

  - name: Install apache2 on Debian systems
    ansible.builtin.apt:
      name: apache2
      state: present
    when: ansible_facts['os_family'] == "Debian"

Testing Variables

You can test variables in many ways with the when clause:

Condition TypeExampleDescription
Equalitywhen: my_var == "value"True when variable equals value
Inequalitywhen: my_var != "value"True when variable doesn't equal value
Booleanwhen: run_taskTrue when variable is truthy
Definedwhen: my_var is definedTrue when variable exists
Undefinedwhen: my_var is not definedTrue when variable doesn't exist
In listwhen: item in my_listTrue when item is in the list
Greater thanwhen: count > 5Standard numeric comparisons
Less thanwhen: memory_mb < 512Compare numeric values

Testing Facts

Ansible facts provide information about managed hosts. Common facts used in conditionals:

Common fact tests
# Test operating system family
when: ansible_facts['os_family'] == "RedHat"

# Test specific distribution
when: ansible_facts['distribution'] == "CentOS"

# Test distribution version
when: ansible_facts['distribution_major_version'] == "9"

# Test available memory
when: ansible_facts['memfree_mb'] >= 512

# Test if running in a virtual machine
when: ansible_facts['virtualization_type'] == "kvm"
⚠️ Important

When testing strings, be careful with case sensitivity. "RedHat" is different from "redhat". Use the lower filter if needed: when: ansible_facts['os_family'] | lower == "redhat"

Advanced Conditionals

Combine multiple conditions and test registered variables for powerful conditional logic.

Multiple Conditions with AND

When you need all conditions to be true, use a list format or the and operator:

AND conditions - List format (implicit AND)
- name: Install package on RHEL 9 web servers
  ansible.builtin.dnf:
    name: httpd
    state: present
  when:
    - ansible_facts['os_family'] == "RedHat"
    - ansible_facts['distribution_major_version'] == "9"
    - inventory_hostname in groups['webservers']

Multiple Conditions with OR

When you need any condition to be true, use the or operator:

OR conditions
- name: Install on Red Hat or Fedora
  ansible.builtin.dnf:
    name: vim-enhanced
    state: present
  when: ansible_facts['distribution'] == "RedHat" or
        ansible_facts['distribution'] == "Fedora"

Combining AND and OR

Use parentheses to group conditions when combining and and or:

Combined AND/OR with parentheses
- name: Configure production web servers
  ansible.builtin.template:
    src: httpd.conf.j2
    dest: /etc/httpd/conf/httpd.conf
  when: (ansible_facts['os_family'] == "RedHat" or
        ansible_facts['os_family'] == "Debian") and
        environment == "production"

Testing Registered Variables

Use the registerStores the result of a task in a variable that can be used by subsequent tasks for conditionals or data extraction. keyword to capture task output and test it in conditions:

Using registered variables in conditions
tasks:
  - name: Check if service is running
    ansible.builtin.command:
      cmd: systemctl is-active httpd
    register: httpd_status
    ignore_errors: true
    changed_when: false

  - name: Start httpd if not running
    ansible.builtin.service:
      name: httpd
      state: started
    when: httpd_status.rc != 0

  - name: Display status message
    ansible.builtin.debug:
      msg: "Service was already running"
    when: httpd_status.rc == 0

Common Registered Variable Tests

TestDescription
result.rc == 0Command exited successfully (return code 0)
result is succeededTask completed without failure
result is failedTask failed
result is changedTask made changes
result is skippedTask was skipped
'string' in result.stdoutString found in command output
result.stdout_lines | length > 0Command produced output

Loop Basics

Loops allow you to repeat a task multiple times with different values, reducing code duplication and making playbooks more maintainable.

The loop Keyword

The loopIterates over a list, running the task once for each item. The current item is available as the 'item' variable. keyword is the modern, recommended way to iterate in Ansible (replacing the older with_* plugins).

Basic loop example
tasks:
  - name: Create multiple users
    ansible.builtin.user:
      name: "{{ item }}"
      state: present
    loop:
      - alice
      - bob
      - charlie
      - diana
💡 Package Installation Best Practice

For package installation, pass the entire list to name instead of looping—it's more efficient as it makes a single transaction:

- name: Install packages (efficient - single transaction)
  ansible.builtin.dnf:
    name:
      - httpd
      - mariadb-server
      - php
    state: present

Looping Over a List Variable

Loop with variable list
vars:
  packages_to_install:
    - httpd
    - firewalld
    - vim-enhanced

tasks:
  - name: Install required packages
    ansible.builtin.dnf:
      name: "{{ item }}"
      state: present
    loop: "{{ packages_to_install }}"

Looping Over Dictionaries (Hash)

When looping over complex data structures with multiple attributes, access them using item.key syntax:

Loop over list of dictionaries
vars:
  users:
    - name: alice
      groups: developers,wheel
      shell: /bin/bash
    - name: bob
      groups: admins
      shell: /bin/zsh
    - name: charlie
      groups: developers
      shell: /bin/bash

tasks:
  - name: Create users with full configuration
    ansible.builtin.user:
      name: "{{ item.name }}"
      groups: "{{ item.groups }}"
      shell: "{{ item.shell }}"
      state: present
    loop: "{{ users }}"

Using the dict2items Filter

Convert a dictionary to a list of key/value pairs for iteration:

dict2items filter example
vars:
  user_uids:
    alice: 1001
    bob: 1002
    charlie: 1003

tasks:
  - name: Create users with specific UIDs
    ansible.builtin.user:
      name: "{{ item.key }}"
      uid: "{{ item.value }}"
      state: present
    loop: "{{ user_uids | dict2items }}"

Loop Control

Fine-tune loop behavior with the loop_control directive and access extended loop information.

The loop_control Directive

The loop_controlA directive that modifies loop behavior, including output labeling, variable naming, indexing, and timing between iterations. directive provides options to customize loop execution:

🏷️
label
Control what's displayed during loop execution to reduce verbose output.
📛
loop_var
Rename the default item variable to avoid conflicts in nested loops.
🔢
index_var
Track the current iteration index (0-based).
⏸️
pause
Add a delay (in seconds) between loop iterations.
loop_control with label
- name: Create users with custom output label
  ansible.builtin.user:
    name: "{{ item.name }}"
    uid: "{{ item.uid }}"
    groups: "{{ item.groups }}"
  loop:
    - name: alice
      uid: 1001
      groups: developers,wheel
    - name: bob
      uid: 1002
      groups: admins
  loop_control:
    label: "{{ item.name }}"  # Shows only username instead of entire dict
loop_control with index_var
- name: Display items with index
  ansible.builtin.debug:
    msg: "Item {{ idx }}: {{ server }}"
  loop:
    - web1.example.com
    - web2.example.com
    - db1.example.com
  loop_control:
    index_var: idx
    loop_var: server

Extended Loop Variables

Enable extended loop information with extended: true:

VariableDescription
ansible_loop.indexCurrent iteration (1-indexed)
ansible_loop.index0Current iteration (0-indexed)
ansible_loop.firstTrue if this is the first iteration
ansible_loop.lastTrue if this is the last iteration
ansible_loop.lengthTotal number of items in the loop
ansible_loop.previtemItem from the previous iteration
ansible_loop.nextitemItem from the next iteration
Extended loop variables example
- name: Process items with position awareness
  ansible.builtin.debug:
    msg: "Processing {{ item }} ({{ ansible_loop.index }}/{{ ansible_loop.length }})"
  loop:
    - first_item
    - middle_item
    - last_item
  loop_control:
    extended: true

- name: Special handling for first and last
  ansible.builtin.debug:
    msg: "{{ 'START: ' if ansible_loop.first else '' }}{{ item }}{{ ' :END' if ansible_loop.last else '' }}"
  loop: "{{ items }}"
  loop_control:
    extended: true

Register with Loops

When using register with loops, the registered variable contains a results list:

Registering loop results
- name: Check multiple services
  ansible.builtin.command:
    cmd: "systemctl is-active {{ item }}"
  loop:
    - httpd
    - mariadb
    - firewalld
  register: service_status
  ignore_errors: true
  changed_when: false

- name: Display inactive services
  ansible.builtin.debug:
    msg: "{{ item.item }} is not running"
  loop: "{{ service_status.results }}"
  when: item.rc != 0
  loop_control:
    label: "{{ item.item }}"
💡 Combining Loops and Conditionals

You can use when with loops. The condition is evaluated for each item, so some items may be processed while others are skipped.

Handler Concepts

Handlers are special tasks that only run when notified, making them perfect for actions like service restarts that should only happen when configuration changes.

How Handlers Work

HandlersSpecial tasks defined in a handlers section that only execute when notified by a task. They run once at the end of the play, regardless of how many times notified. have three key characteristics:

🔔
Notification Triggered
Handlers only run when a task that notifies them reports a "changed" status.
1️⃣
Run Once Per Play
Each handler runs only once per play, regardless of how many tasks notify it.
⏰
End of Play Execution
Handlers execute after all tasks in the play complete, not immediately when notified.

Basic Handler Syntax

Handler example - Web server configuration
---
- name: Configure web server
  hosts: webservers
  become: true

  tasks:
    - name: Install httpd package
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Copy main configuration file
      ansible.builtin.copy:
        src: files/httpd.conf
        dest: /etc/httpd/conf/httpd.conf
        owner: root
        group: root
        mode: '0644'
      notify: Restart httpd

    - name: Copy SSL configuration
      ansible.builtin.copy:
        src: files/ssl.conf
        dest: /etc/httpd/conf.d/ssl.conf
      notify: Restart httpd

  handlers:
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Handler Execution Flow

When Do Handlers Run?
Task 1: Install httpd
STATUS: ok (no change) — no notification
↓
Task 2: Copy httpd.conf
STATUS: changed → notifies "Restart httpd"
↓
Task 3: Copy ssl.conf
STATUS: changed → notifies "Restart httpd"
↓ All tasks complete
🔔 Handler: Restart httpd
RUNS ONCE (despite 2 notifications)

Notifying Multiple Handlers

A single task can notify multiple handlers using a list:

Notifying multiple handlers
tasks:
  - name: Update configuration
    ansible.builtin.template:
      src: config.j2
      dest: /etc/myapp/config.conf
    notify:
      - Validate configuration
      - Restart application
      - Clear cache

handlers:
  - name: Validate configuration
    ansible.builtin.command:
      cmd: /usr/bin/myapp --validate-config

  - name: Restart application
    ansible.builtin.service:
      name: myapp
      state: restarted

  - name: Clear cache
    ansible.builtin.file:
      path: /var/cache/myapp
      state: absent
💡 Handler Order

Handlers run in the order they are defined in the handlers section, not the order they are notified. Plan your handler order accordingly.

Advanced Handlers

Learn about handler listening, flushing handlers early, and controlling handler behavior during failures.

The listen Directive

The listenAllows multiple handlers to respond to a single notification topic, enabling flexible handler grouping and execution. directive allows multiple handlers to "listen" to a common topic:

Handlers with listen directive
tasks:
  - name: Update web server configuration
    ansible.builtin.template:
      src: httpd.conf.j2
      dest: /etc/httpd/conf/httpd.conf
    notify: restart web services  # Notify topic, not handler name

handlers:
  - name: Restart httpd
    ansible.builtin.service:
      name: httpd
      state: restarted
    listen: restart web services

  - name: Restart php-fpm
    ansible.builtin.service:
      name: php-fpm
      state: restarted
    listen: restart web services

  - name: Clear varnish cache
    ansible.builtin.command:
      cmd: varnishadm "ban req.url ~ ."
    listen: restart web services

Flushing Handlers

Normally handlers run at the end of a play. Use meta: flush_handlersA special task that forces all pending handlers to run immediately, before continuing with remaining tasks. to run them immediately:

flush_handlers example
tasks:
  - name: Update firewall configuration
    ansible.builtin.template:
      src: firewall.conf.j2
      dest: /etc/firewalld/firewalld.conf
    notify: Restart firewalld

  - name: Flush handlers to restart firewall now
    ansible.builtin.meta: flush_handlers

  - name: Configure application (needs firewall running)
    ansible.builtin.template:
      src: app.conf.j2
      dest: /etc/myapp/app.conf

handlers:
  - name: Restart firewalld
    ansible.builtin.service:
      name: firewalld
      state: restarted

Handlers and Task Failures

By default, if a task fails, handlers are not run. Use force_handlers: true to change this:

Force handlers on failure
---
- name: Configure services with guaranteed handler execution
  hosts: all
  force_handlers: true  # Handlers run even if tasks fail

  tasks:
    - name: Update configuration
      ansible.builtin.template:
        src: config.j2
        dest: /etc/myapp/config.conf
      notify: Restart myapp

    - name: This task might fail
      ansible.builtin.command:
        cmd: /usr/local/bin/risky-operation.sh

  handlers:
    - name: Restart myapp
      ansible.builtin.service:
        name: myapp
        state: restarted
⚠️ Handler Behavior Summary

Default behavior: Handlers run at end of play, only if notified, only once, and NOT if a task fails.
With force_handlers: Handlers run even after task failures.
With flush_handlers: Pending handlers run immediately at that point in the play.

Handling Failures

Control how Ansible responds to task failures with options to ignore errors, define custom failure conditions, and manage change reporting.

Ignoring Errors

Use ignore_errorsAllows playbook execution to continue even if this task fails. The task is still marked as failed in the play recap statistics. to continue execution when a task fails:

ignore_errors example
tasks:
  - name: Try to stop a service that might not exist
    ansible.builtin.service:
      name: optional-service
      state: stopped
    ignore_errors: true

  - name: This task runs even if previous failed
    ansible.builtin.debug:
      msg: "Continuing with playbook execution"
⚠️ Use With Caution

While ignore_errors prevents playbook failure, the task is still reported as failed. Consider using failed_when: false if you want to completely suppress failure status.

Custom Failure Conditions

Use failed_whenDefines custom conditions that determine when a task should be considered failed, overriding the default failure detection. to define when a task should fail:

failed_when examples
tasks:
  # Fail based on output content, not return code
  - name: Run deployment script
    ansible.builtin.command:
      cmd: /opt/scripts/deploy.sh
    register: deploy_result
    failed_when: "'ERROR' in deploy_result.stderr"

  # Fail on specific return codes
  - name: Check application status
    ansible.builtin.command:
      cmd: /opt/app/healthcheck.sh
    register: health_check
    failed_when: health_check.rc > 1  # rc=1 is warning, >1 is error

  # Never fail (useful for checking status)
  - name: Check if service exists
    ansible.builtin.command:
      cmd: systemctl status myservice
    register: service_status
    failed_when: false  # Never fails, check rc in next task

Custom Change Detection

Use changed_whenDefines custom conditions that determine when a task should report a change, controlling handler notifications and play statistics. to control when a task reports as "changed":

changed_when examples
tasks:
  # Never report change (for information gathering)
  - name: Get current kernel version
    ansible.builtin.command:
      cmd: uname -r
    register: kernel_version
    changed_when: false

  # Change based on output content
  - name: Apply database migrations
    ansible.builtin.command:
      cmd: /opt/app/migrate.sh
    register: migration
    changed_when: "'Migrations applied' in migration.stdout"

  # Combined conditions
  - name: Update application
    ansible.builtin.command:
      cmd: /opt/app/update.sh
    register: update_result
    changed_when:
      - update_result.rc == 0
      - "'Updated' in update_result.stdout"

Fail Fast Options

Control playbook behavior when managing multiple hosts:

OptionDescription
any_errors_fatal: trueStop playbook on ALL hosts if any host fails
max_fail_percentage: 30Abort if more than 30% of hosts fail
Fail fast options
---
- name: Critical deployment - fail fast
  hosts: production
  any_errors_fatal: true  # One failure stops everything
  tasks:
    # ...

- name: Rolling update - tolerate some failures
  hosts: webservers
  max_fail_percentage: 25  # Continue if ≤25% fail
  serial: 5  # Process 5 hosts at a time
  tasks:
    # ...
💡 Best Practice

Always use changed_when: false for tasks that only gather information (like command or shell used for status checks). This maintains accurate change reporting and prevents unintended handler notifications.

Blocks

Group related tasks together and implement try/catch/finally error handling patterns for robust automation.

What are Blocks?

BlocksA way to group multiple tasks together. Tasks in a block can share common attributes and participate in error handling with rescue and always sections. group tasks and enable you to:

  • Apply common attributes (like when, become) to multiple tasks
  • Implement error handling with rescue and always sections
  • Create logical groupings for better playbook organization

Block Error Handling Structure

Block / Rescue / Always Flow
block:
Main tasks - attempt to execute these first
↓ If any task in block fails...
rescue:
Error recovery tasks - only run on block failure
↓ Always executed (success or failure)
always:
Cleanup tasks - run regardless of outcome
Complete block with rescue and always
tasks:
  - name: Upgrade application with rollback capability
    block:
      - name: Create backup of current version
        ansible.builtin.copy:
          src: /opt/app/
          dest: /opt/app.backup/
          remote_src: true

      - name: Deploy new version
        ansible.builtin.unarchive:
          src: files/app-v2.0.tar.gz
          dest: /opt/app/

      - name: Run database migrations
        ansible.builtin.command:
          cmd: /opt/app/migrate.sh

      - name: Verify deployment with health check
        ansible.builtin.uri:
          url: http://localhost:8080/health
          status_code: 200

    rescue:
      - name: Rollback - Restore from backup
        ansible.builtin.copy:
          src: /opt/app.backup/
          dest: /opt/app/
          remote_src: true

      - name: Log the failure details
        ansible.builtin.debug:
          msg: "Deployment failed at: {{ ansible_failed_task.name }}"

    always:
      - name: Restart application service
        ansible.builtin.service:
          name: myapp
          state: restarted

      - name: Clean up backup directory
        ansible.builtin.file:
          path: /opt/app.backup
          state: absent

Special Variables in Rescue

When a rescue block runs, special variables provide information about the failure:

VariableDescription
ansible_failed_taskDictionary with info about the failed task (name, action, args)
ansible_failed_resultThe registered result of the failed task (stdout, stderr, rc, etc.)
Using failure information in rescue
rescue:
  - name: Display detailed failure information
    ansible.builtin.debug:
      msg: |
        Task '{{ ansible_failed_task.name }}' failed.
        Action: {{ ansible_failed_task.action }}
        Error: {{ ansible_failed_result.msg | default('Unknown error') }}

  - name: Send failure notification
    ansible.builtin.mail:
      to: admin@example.com
      subject: "Deployment Failed: {{ ansible_failed_task.name }}"
      body: "{{ ansible_failed_result | to_nice_yaml }}"
❌ Rescue Limitations

The rescue section only runs for task failures. It does NOT run for:
• Syntax errors in the playbook
• Unreachable hosts
• Undefined variables
• Connection failures

Blocks Without Error Handling

Blocks can also be used simply to apply common attributes to multiple tasks:

Block with shared attributes
tasks:
  - name: Configure web servers only
    block:
      - name: Install httpd
        ansible.builtin.dnf:
          name: httpd
          state: present

      - name: Configure httpd
        ansible.builtin.template:
          src: httpd.conf.j2
          dest: /etc/httpd/conf/httpd.conf

      - name: Start httpd
        ansible.builtin.service:
          name: httpd
          state: started
          enabled: true
    when: inventory_hostname in groups['webservers']
    become: true
