The when Clause

Conditionals allow you to control whether a task runs based on variables, facts, or registered results.

Understanding Conditionals

The whenA task attribute that evaluates a Jinja2 expression. The task runs only if the expression evaluates to true. clause is used to conditionally execute tasks. Ansible evaluates the condition before running the task, and skips it if the condition is false.

💡 Key Point

The when clause uses raw Jinja2 expressions without the double curly braces {{ }}. Variables are referenced by name directly.

Basic when Syntax

Simple conditional example
tasks:
  - name: Install httpd on Red Hat systems
    ansible.builtin.dnf:
      name: httpd
      state: present
    when: ansible_facts['os_family'] == "RedHat"

  - name: Install apache2 on Debian systems
    ansible.builtin.apt:
      name: apache2
      state: present
    when: ansible_facts['os_family'] == "Debian"

Testing Variables

Condition TypeExampleDescription
Equalitywhen: my_var == "value"True when variable equals value
Inequalitywhen: my_var != "value"True when variable doesn't equal value
Booleanwhen: run_taskTrue when variable is truthy

⚠️ Important

When using when with a list of conditions, all conditions must be true (logical AND). Each condition is a separate list item.

Advanced Conditionals

Combine multiple conditions and test registered variables for powerful conditional logic.

Multiple Conditions

Combine conditions using logical operatorsBoolean operators (and, or, not) that combine multiple conditions. Parentheses can group sub-expressions.:

AND conditions (all must be true)
# Method 1: List format (implicit AND)
- name: Install package on RHEL web servers
  ansible.builtin.dnf:
    name: httpd
    state: present
  when:
    - ansible_facts['os_family'] == "RedHat"
    - inventory_hostname in groups['webservers']

# Method 2: OR operator
- name: Install on Red Hat or Fedora
  ansible.builtin.dnf:
    name: vim
    state: present
  when: ansible_facts['distribution'] == "RedHat" or ansible_facts['distribution'] == "Fedora"

Testing Registered Variables

Use the registerStores the result of a task in a variable that can be used by subsequent tasks for conditionals or data extraction. keyword to capture task output and test it in conditions:

Using registered variables in conditions
tasks:
  - name: Check if service is running
    ansible.builtin.command:
      cmd: systemctl is-active httpd
    register: httpd_status
    ignore_errors: true
    changed_when: false

  - name: Start httpd if not running
    ansible.builtin.service:
      name: httpd
      state: started
    when: httpd_status.rc != 0

Loop Basics

Loops allow you to repeat a task multiple times with different values, reducing code duplication.

The loop Keyword

The loopIterates over a list, running the task once for each item. The current item is available as the 'item' variable. keyword is the modern way to iterate in Ansible.

Basic loop example
tasks:
  - name: Install multiple packages
    ansible.builtin.dnf:
      name: "{{ item }}"
      state: present
    loop:
      - httpd
      - mariadb-server
      - php
      - php-mysqlnd
💡 Best Practice

For package installation, pass the entire list to name instead of looping for better efficiency:

- name: Install packages (efficient)
  ansible.builtin.dnf:
    name:
      - httpd
      - mariadb-server
    state: present

Looping Over Complex Data

Complex data loop
vars:
  users:
    - name: alice
      groups: developers,wheel
      shell: /bin/bash
    - name: bob
      groups: admins
      shell: /bin/zsh

tasks:
  - name: Create users with full configuration
    ansible.builtin.user:
      name: "{{ item.name }}"
      groups: "{{ item.groups }}"
      shell: "{{ item.shell }}"
      state: present
    loop: "{{ users }}"

Loop Control

Fine-tune loop behavior with the loop_control directive.

The loop_control Directive

🏷️
label
Control what's displayed during loop execution to reduce verbose output.
📛
loop_var
Rename the default item variable to avoid conflicts.
🔢
index_var
Track the current iteration index (0-based).
⏸️
pause
Add a delay between loop iterations.
loop_control examples
tasks:
  - name: Create users with custom label
    ansible.builtin.user:
      name: "{{ item.name }}"
      uid: "{{ item.uid }}"
    loop:
      - name: alice
        uid: 1001
      - name: bob
        uid: 1002
    loop_control:
      label: "{{ item.name }}"

  - name: Show item with index
    ansible.builtin.debug:
      msg: "Item {{ idx }}: {{ item }}"
    loop:
      - first
      - second
    loop_control:
      index_var: idx

Handler Concepts

Handlers are special tasks that only run when notified, perfect for service restarts.

How Handlers Work

HandlersSpecial tasks that only execute when notified. They run once at the end of the play, regardless of how many times notified. have three key characteristics:

🔔
Notification Triggered
Only run when a task reports "changed" status.
1️⃣
Run Once
Each handler runs only once per play.
⏰
End of Play
Execute after all tasks complete.
Handler example
---
- name: Configure web server
  hosts: webservers
  become: true

  tasks:
    - name: Copy configuration file
      ansible.builtin.copy:
        src: httpd.conf
        dest: /etc/httpd/conf/httpd.conf
      notify: Restart httpd

    - name: Copy SSL configuration
      ansible.builtin.copy:
        src: ssl.conf
        dest: /etc/httpd/conf.d/ssl.conf
      notify: Restart httpd

  handlers:
    - name: Restart httpd
      ansible.builtin.service:
        name: httpd
        state: restarted

Handler Execution Flow

When Do Handlers Run?
Task 1: Install httpd
STATUS: ok (no change)
↓
Task 2: Copy httpd.conf
STATUS: changed → notifies handler
↓
Task 3: Copy ssl.conf
STATUS: changed → notifies handler
↓ All tasks complete
🔔 Handler: Restart httpd
RUNS ONCE (despite 2 notifications)
💡 Handler Order

Handlers run in the order they are defined in the handlers section, not the order they are notified.

Handling Failures

Control how Ansible responds to task failures with options to ignore errors and define custom failure conditions.

Ignoring Errors

Use ignore_errorsAllows playbook execution to continue even if this task fails. The task is still marked as failed in statistics. to continue execution when a task fails:

ignore_errors example
- name: Try to stop a service that might not exist
  ansible.builtin.service:
    name: optional-service
    state: stopped
  ignore_errors: true

Custom Failure Conditions

Use failed_whenDefines custom conditions that determine when a task should be considered failed. to define when a task should fail:

failed_when examples
tasks:
  # Fail based on output content
  - name: Run deployment script
    ansible.builtin.command:
      cmd: /opt/deploy.sh
    register: deploy_result
    failed_when: "'ERROR' in deploy_result.stderr"

  # Never fail (useful for checking status)
  - name: Check service status
    ansible.builtin.command:
      cmd: systemctl is-active myservice
    register: service_status
    failed_when: false

Custom Change Detection

Use changed_whenDefines custom conditions that determine when a task should report a change. to control when a task reports as "changed":

changed_when examples
tasks:
  # Never report change (for status checks)
  - name: Get current user
    ansible.builtin.command:
      cmd: whoami
    register: current_user
    changed_when: false

  # Change based on output
  - name: Apply database migrations
    ansible.builtin.command:
      cmd: /opt/migrate.sh
    register: migration
    changed_when: "'Migrations applied' in migration.stdout"
💡 Best Practice

Always use changed_when: false for tasks that only gather information to maintain accurate change reporting.

Blocks

Group related tasks together and implement try/catch/finally error handling patterns.

What are Blocks?

BlocksA way to group multiple tasks together. Tasks in a block can share common attributes and participate in error handling. group tasks and allow you to apply common attributes. They also provide error handling similar to try/catch.

Block Error Handling

Block Error Handling Flow
block:
Main tasks - try to execute these
↓ If any task fails
rescue:
Error recovery tasks - run on failure
↓ Always runs
always:
Cleanup tasks - run regardless of outcome
Complete block with rescue and always
tasks:
  - name: Upgrade application with rollback
    block:
      - name: Create backup
        ansible.builtin.copy:
          src: /opt/app
          dest: /opt/app.backup
          remote_src: true

      - name: Deploy new version
        ansible.builtin.unarchive:
          src: app-v2.0.tar.gz
          dest: /opt/app

      - name: Verify deployment
        ansible.builtin.uri:
          url: http://localhost:8080/health
          status_code: 200

    rescue:
      - name: Rollback - Restore from backup
        ansible.builtin.copy:
          src: /opt/app.backup
          dest: /opt/app
          remote_src: true

      - name: Log failure
        ansible.builtin.debug:
          msg: "Error: {{ ansible_failed_task.name }}"

    always:
      - name: Restart application service
        ansible.builtin.service:
          name: myapp
          state: restarted

      - name: Remove backup
        ansible.builtin.file:
          path: /opt/app.backup
          state: absent

Special Variables in Rescue

VariableDescription
ansible_failed_taskInformation about the task that triggered rescue
ansible_failed_resultThe result of the failed task
❌ Rescue Limitations

The rescue section only runs for task failures, not for syntax errors, unreachable hosts, or undefined variables.
