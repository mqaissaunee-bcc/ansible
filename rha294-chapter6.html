Introduction to Imports and Includes

Ansible provides two mechanisms for incorporating external content: imports (static) and includes (dynamic). Understanding the difference is crucial for building maintainable automation.

Why Organize Playbooks?

As your automation grows, you'll encounter several challenges with monolithic playbooks:

  • Files become too long to navigate and maintain
  • Multiple team members can't work on the same file simultaneously
  • Task logic cannot be reused across different playbooks
  • Testing individual components becomes difficult
Static Imports

Content is processed when the playbook is parsed, before execution begins.

  • Pre-processed at parse time
  • Cannot use loops
  • Visible in --list-tasks
  • Conditions applied to each imported task
  • Variable values locked at parse time
Dynamic Includes

Content is processed when the task is reached during playbook execution.

  • Processed at runtime
  • Supports loops
  • Not visible in --list-tasks
  • Conditions evaluated once for include
  • Variable values resolved at runtime

Available Modules

Module Type What It Imports/Includes
import_playbook Static Entire playbooks (at play level only)
import_tasks Static Task files
import_role Static Roles
include_tasks Dynamic Task files
include_role Dynamic Roles
include_vars Dynamic Variable files
💡 Pro Tip

The older include module is deprecated. Always use the specific import_* or include_* modules to make your intent clear.

Importing Playbooks

Use import_playbook to combine multiple playbooks into a single master playbook, enabling modular organization of complex automation projects.

Understanding import_playbook

The import_playbookImports an entire playbook file at parse time. Must be used at the play level, not within a play's tasks section. directive allows you to import entire playbooks. This is useful for creating a master "site.yml" that orchestrates your entire infrastructure configuration.

⚠️ Important

import_playbook must be used at the play level, not inside a play's tasks section. It imports complete plays, not individual tasks.

Basic Syntax

site.yml - Master Playbook 
---
# Master playbook that imports all component playbooks

- name: Apply base configuration to all hosts
  hosts: all
  tasks:
    - name: Ensure base packages are installed
      ansible.builtin.dnf:
        name: vim
        state: present

# Import additional playbooks at the play level
- ansible.builtin.import_playbook: webservers.yml
- ansible.builtin.import_playbook: dbservers.yml
- ansible.builtin.import_playbook: monitoring.yml

Imported Playbook Example

webservers.yml 
---
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    - name: Install Apache
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Start and enable Apache
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

Execution Flow

How import_playbook Works
Step 1
Parse site.yml
↓
Step 2
Import all referenced playbooks
↓
Step 3
Combine into single execution plan
↓
Step 4
Execute plays in order

Use Cases

🏢
Infrastructure as Code
Create a site.yml that configures your entire infrastructure with one command: ansible-playbook site.yml
👥
Team Collaboration
Different team members can maintain separate playbooks (webservers.yml, databases.yml) without conflicts.
🎯
Selective Execution
Run the full site.yml or individual playbooks independently depending on your needs.

Importing Task Files

Use import_tasks to statically include external task files into your playbooks at parse time.

Understanding import_tasks

The import_tasksStatically imports tasks from an external file. The tasks are processed and added to the playbook at parse time, before execution begins. module reads a task file and inserts its contents directly into the playbook during parsing. This means:

  • Tasks are visible when using ansible-playbook --list-tasks
  • Syntax errors in imported files are caught before execution
  • Variables are resolved at parse time (static values)
  • Cannot be used with loops

Task File Structure

Task files contain only tasks – no play-level attributes like hosts, become, or vars.

tasks/install_apache.yml 
---
# Task file - contains only tasks, no play attributes

- name: Install Apache web server
  ansible.builtin.dnf:
    name: httpd
    state: present

- name: Copy Apache configuration
  ansible.builtin.template:
    src: httpd.conf.j2
    dest: /etc/httpd/conf/httpd.conf
  notify: Restart Apache

- name: Start and enable Apache
  ansible.builtin.service:
    name: httpd
    state: started
    enabled: true

Using import_tasks in a Playbook

main.yml 
---
- name: Configure web servers
  hosts: webservers
  become: true

  handlers:
    - name: Restart Apache
      ansible.builtin.service:
        name: httpd
        state: restarted

  tasks:
    - name: Import Apache installation tasks
      ansible.builtin.import_tasks:
        file: tasks/install_apache.yml

    - name: Import firewall configuration
      ansible.builtin.import_tasks:
        file: tasks/configure_firewall.yml

Passing Variables to Imported Tasks

You can pass variables to imported task files using the vars keyword:

Passing Variables 
tasks:
  - name: Import user creation tasks
    ansible.builtin.import_tasks:
      file: tasks/create_user.yml
    vars:
      username: webadmin
      user_groups: wheel,apache

Conditional Imports

When you use when with import_tasks, the condition is applied to each imported task individually, not to the import itself.

Conditional Import 
tasks:
  - name: Import RHEL-specific tasks
    ansible.builtin.import_tasks:
      file: tasks/rhel_config.yml
    when: ansible_facts['os_family'] == 'RedHat'
⚠️ Condition Behavior

With import_tasks, the when condition is copied to every task in the imported file. This means each task is evaluated independently, which may have performance implications if the file contains many tasks.

Listing Imported Tasks

Since imports are processed at parse time, you can see all tasks using --list-tasks:

Command Line 
# List all tasks including imported ones
$ ansible-playbook main.yml --list-tasks

playbook: main.yml

  play #1 (webservers): Configure web servers   TAGS: []
    tasks:
      Install Apache web server                  TAGS: []
      Copy Apache configuration                  TAGS: []
      Start and enable Apache                    TAGS: []
      Configure firewall rules                   TAGS: []

Including Task Files

Use include_tasks to dynamically load task files at runtime, enabling loops, variable filenames, and conditional loading.

Understanding include_tasks

The include_tasksDynamically includes tasks from an external file at runtime. The tasks are processed when the include_tasks task is executed, not at parse time. module loads task files when the task is reached during execution. This provides greater flexibility:

  • Can use loops to include multiple files
  • Can use variables in the filename
  • Conditions are evaluated once for the include
  • Tasks are NOT visible in --list-tasks

Basic Usage

Using include_tasks 
---
- name: Configure servers
  hosts: all
  become: true

  tasks:
    - name: Include common tasks
      ansible.builtin.include_tasks:
        file: tasks/common.yml

    - name: Include environment-specific tasks
      ansible.builtin.include_tasks:
        file: "tasks/{{ env_type }}.yml"

Using Loops with include_tasks

One of the most powerful features of include_tasks is the ability to use loops. This allows you to include multiple task files dynamically.

Include with Loop 
---
- name: Configure multiple services
  hosts: servers
  become: true
  vars:
    services:
      - apache
      - mysql
      - php

  tasks:
    - name: Include service configuration tasks
      ansible.builtin.include_tasks:
        file: "tasks/{{ item }}.yml"
      loop: "{{ services }}"
💡 Loop Behavior

When using a loop, include_tasks includes the file once for each item in the loop. All tasks in the included file are executed before moving to the next loop iteration.

Variable Filenames

Include tasks based on facts or variables for dynamic, adaptive playbooks:

OS-Specific Includes 
tasks:
  - name: Include OS-specific tasks
    ansible.builtin.include_tasks:
      file: "tasks/{{ ansible_facts['os_family'] }}.yml"

  # This will include:
  # - tasks/RedHat.yml on RHEL/CentOS/Fedora
  # - tasks/Debian.yml on Debian/Ubuntu

Conditional Includes

With include_tasks, the when condition is evaluated once. If true, all tasks in the file are executed; if false, the entire file is skipped.

Conditional Include 
tasks:
  - name: Include development tasks
    ansible.builtin.include_tasks:
      file: tasks/development.yml
    when: env == 'development'

  - name: Include production hardening
    ansible.builtin.include_tasks:
      file: tasks/production_hardening.yml
    when: env == 'production'

Runtime Output

When you run a playbook with include_tasks, you'll see the include task itself, followed by the included tasks:

Execution Output 
TASK [Include service configuration tasks] *********************
included: tasks/apache.yml for server1, server2

TASK [Install Apache] ******************************************
changed: [server1]
changed: [server2]

TASK [Include service configuration tasks] *********************
included: tasks/mysql.yml for server1, server2

TASK [Install MySQL] *******************************************
changed: [server1]
changed: [server2]

Import vs Include: Making the Right Choice

Understanding when to use static imports versus dynamic includes is key to building efficient, maintainable automation.

Feature Comparison

Feature import_tasks (Static) include_tasks (Dynamic)
Processing Time Parse time (before execution) Runtime (when task is reached)
--list-tasks Visibility ✅ Shows all imported tasks ❌ Shows only include statement
Loop Support ❌ Not supported ✅ Fully supported
Variable Filename ⚠️ Limited (parse-time values) ✅ Full runtime variables
when Behavior Applied to each task Applied once to include
Handler Triggers ✅ Work as expected ⚠️ Use with caution
Syntax Validation ✅ Early (parse time) ❌ Late (runtime)
Tags Applied to all tasks Applied to include only

Decision Guide

When to Use Each Method
Use Import
  • Tasks should be visible in --list-tasks
  • You need early syntax validation
  • Task file is always executed (no loops needed)
  • Handlers need to be triggered reliably
  • You want tags applied to all tasks
Use Include
  • You need to use loops
  • Filename depends on runtime variables
  • Tasks might be conditionally skipped entirely
  • Loading tasks based on gathered facts
  • Maximum flexibility is required

Common Patterns

OS-Specific Configuration

Load different tasks based on the operating system:

Dynamic OS Selection 
tasks:
  # Use include_tasks because filename is dynamic
  - name: Include OS-specific package tasks
    ansible.builtin.include_tasks:
      file: "tasks/packages_{{ ansible_facts['os_family'] | lower }}.yml"

Environment-Based Configuration

Apply different settings based on deployment environment:

Environment Selection 
tasks:
  - name: Import base configuration
    ansible.builtin.import_tasks:
      file: tasks/base.yml

  - name: Include environment tasks
    ansible.builtin.include_tasks:
      file: "tasks/{{ deploy_env }}.yml"
    vars:
      deploy_env: "{{ lookup('env', 'DEPLOY_ENV') | default('development') }}"

Service Configuration Loop

Configure multiple services using a loop:

Service Loop Pattern 
- name: Configure LAMP stack
  hosts: webservers
  vars:
    lamp_services:
      - name: apache
        port: 80
      - name: mysql
        port: 3306
      - name: php-fpm
        port: 9000

  tasks:
    - name: Configure each service
      ansible.builtin.include_tasks:
        file: "tasks/configure_{{ item.name }}.yml"
      loop: "{{ lamp_services }}"
      loop_control:
        label: "{{ item.name }}"
📖 Best Practice

Use import_tasks as your default choice for straightforward task organization. Switch to include_tasks only when you need its dynamic capabilities (loops, variable filenames, or runtime conditions).

Host and Group Variables

Organize variables efficiently using dedicated directories for host-specific and group-specific configurations.

Variable File Organization

Ansible automatically loads variables from special directories named group_varsA directory containing variable files that apply to hosts based on their group membership. Files are named after the group they apply to. and host_varsA directory containing variable files that apply to specific individual hosts. Files are named after the hostname.. These directories can be located adjacent to your inventory file or playbook.

project/
├── ansible.cfg
├── inventory
├── group_vars/
│ ├── all.yml # Variables for all hosts
│ ├── webservers.yml # Variables for webservers group
│ └── dbservers.yml # Variables for dbservers group
├── host_vars/
│ ├── web1.example.com.yml # Variables for specific host
│ └── db1.example.com.yml
└── site.yml

group_vars Directory

Files in group_vars/ are automatically loaded based on group membership:

group_vars/all.yml 
---
# Variables applied to ALL hosts
ntp_server: time.example.com
dns_servers:
  - 192.168.1.10
  - 192.168.1.11
timezone: America/New_York
admin_email: admin@example.com
group_vars/webservers.yml 
---
# Variables for hosts in the webservers group
http_port: 80
https_port: 443
web_root: /var/www/html
max_clients: 200
web_packages:
  - httpd
  - mod_ssl
  - php

host_vars Directory

Files in host_vars/ provide host-specific overrides:

host_vars/web1.example.com.yml 
---
# Variables specific to web1.example.com
max_clients: 500  # Override group default
ssl_certificate: /etc/pki/tls/certs/web1.crt
ssl_key: /etc/pki/tls/private/web1.key
vhosts:
  - name: main.example.com
    docroot: /var/www/main
  - name: api.example.com
    docroot: /var/www/api

Variable Precedence

When the same variable is defined in multiple places, Ansible uses a precedence order:

Variable Precedence (Highest to Lowest)
Highest Priority
Extra vars (-e)
↓
Play Level
Play vars, vars_files, vars_prompt
↓
Host Specific
host_vars/*
↓
Group Specific
group_vars/*
↓
Lowest Priority
group_vars/all

Using Subdirectories

For complex configurations, you can use subdirectories instead of single files:

group_vars/
├── webservers/ # Directory instead of file
│ ├── vars.yml # Main variables
│ └── vault.yml # Encrypted secrets
└── dbservers/
├── vars.yml
└── vault.yml
💡 Vault Integration

Using subdirectories allows you to keep sensitive data in encrypted vault.yml files while keeping regular variables in plain vars.yml files. Ansible loads all files in the directory automatically.

Best Practices

✓
Use group_vars/all.yml for organization-wide defaults
✓
Create group-specific files matching inventory group names
✓
Use host_vars/ sparingly for true host-specific settings
✓
Store secrets in separate vault-encrypted files
✓
Use meaningful variable names with prefixes (e.g., web_, db_)
✓
Document variables with comments

Lab 6.2 Use include_tasks with Loops

Create a playbook that dynamically includes task files based on a list of services.

1
Create service task files:
tasks/configure_firewall.yml 
---
- name: Configure firewall for {{ service_name }}
  ansible.builtin.debug:
    msg: "Configuring firewall for {{ service_name }} on port {{ service_port }}"
2
Create the playbook with loop:
configure_services.yml 
---
- name: Configure multiple services
  hosts: localhost
  vars:
    services:
      - name: http
        port: 80
      - name: https
        port: 443
      - name: mysql
        port: 3306

  tasks:
    - name: Configure each service
      ansible.builtin.include_tasks:
        file: tasks/configure_firewall.yml
      loop: "{{ services }}"
      vars:
        service_name: "{{ item.name }}"
        service_port: "{{ item.port }}"
3
Run the playbook and observe the output: 
ansible-playbook configure_services.yml
