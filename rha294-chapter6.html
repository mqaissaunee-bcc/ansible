Selecting Hosts with Host Patterns

Host patterns allow you to precisely target which managed hosts from your inventory a play or ad hoc command should affect.

What Are Host Patterns?

A host patternAn expression used in the hosts directive of a play or with ad hoc commands to specify which managed hosts should be targeted. is used in the hosts directive of a play to specify which managed hosts the play should run against. You can reference hosts by name, by group, or use special patterns to combine, intersect, or exclude hosts.

Basic Host Patterns

Pattern Description Example
all or * All hosts in inventory hosts: all
hostname Single specific host hosts: web1.example.com
groupname All hosts in a group hosts: webservers
ungrouped Hosts not in any group (except all) hosts: ungrouped

Wildcard Patterns

Use wildcards to match multiple hosts based on naming patterns:

Wildcard Examples 
# Match all hosts starting with 'web'
hosts: web*

# Match hosts like web1, web2, web3, etc.
hosts: web*.example.com

# Match any host in the example.com domain
hosts: *.example.com

# Match hosts with 'db' anywhere in the name
hosts: *db*

List Patterns (OR Logic)

Use a colon (:) to specify multiple patterns. Hosts matching any pattern are included:

List Pattern Examples 
# All hosts in webservers OR dbservers groups
hosts: webservers:dbservers

# A specific host OR all hosts in a group
hosts: web1.example.com:dbservers

# Multiple groups combined
hosts: webservers:dbservers:monitoring

Intersection Patterns (AND Logic)

Use an ampersand (&) to select hosts that are in both groups:

Intersection Pattern Examples 
# Hosts that are in BOTH webservers AND production
hosts: webservers:&production

# Hosts in webservers AND datacenter1 AND critical
hosts: webservers:&datacenter1:&critical

Exclusion Patterns (NOT Logic)

Use an exclamation mark (!) to exclude hosts from a pattern:

Exclusion Pattern Examples 
# All webservers EXCEPT those in staging
hosts: webservers:!staging

# All hosts EXCEPT dbservers
hosts: all:!dbservers

# Production webservers, but not maintenance hosts
hosts: webservers:&production:!maintenance
⚠️ Shell Escaping

When using host patterns with special characters on the command line, you may need to quote them to prevent shell interpretation: ansible 'webservers:!staging' -m ping

Testing Host Patterns

Use the --list-hosts option to see which hosts match a pattern without running any tasks:

Testing Host Patterns 
# List hosts that match a pattern
$ ansible webservers --list-hosts
  hosts (3):
    web1.example.com
    web2.example.com
    web3.example.com

# Test complex patterns
$ ansible 'webservers:&production' --list-hosts
  hosts (2):
    web1.example.com
    web2.example.com

# List hosts in a playbook without running it
$ ansible-playbook site.yml --list-hosts

Host Pattern Summary

Operator Meaning Example
: OR (union) web:db = hosts in web OR db
:& AND (intersection) web:&prod = hosts in web AND prod
:! NOT (exclusion) web:!test = web hosts NOT in test
* Wildcard *.example.com = all in domain

Introduction to Imports and Includes

Ansible provides two mechanisms for incorporating external content: imports (static) and includes (dynamic). Understanding the difference is crucial for building maintainable automation.

Why Organize Playbooks?

As your automation grows, you'll encounter several challenges with monolithic playbooks:

  • Files become too long to navigate and maintain
  • Multiple team members can't work on the same file simultaneously
  • Task logic cannot be reused across different playbooks
  • Testing individual components becomes difficult
Static Imports

Content is processed when the playbook is parsed, before execution begins.

  • Pre-processed at parse time
  • Cannot use loops
  • Visible in --list-tasks
  • Conditions applied to each imported task
  • Variable values locked at parse time
Dynamic Includes

Content is processed when the task is reached during playbook execution.

  • Processed at runtime
  • Supports loops
  • Not visible in --list-tasks
  • Conditions evaluated once for include
  • Variable values resolved at runtime

Available Modules

Module Type What It Imports/Includes
import_playbook Static Entire playbooks (at play level only)
import_tasks Static Task files
import_role Static Roles
include_tasks Dynamic Task files
include_role Dynamic Roles
include_vars Dynamic Variable files
💡 Pro Tip

The older include module is deprecated. Always use the specific import_* or include_* modules to make your intent clear.

Importing Task Files

Use import_tasks to statically include external task files into your playbooks at parse time.

Understanding import_tasks

The import_tasksStatically imports tasks from an external file. The tasks are processed and added to the playbook at parse time, before execution begins. module reads a task file and inserts its contents directly into the playbook during parsing. This means:

  • Tasks are visible when using ansible-playbook --list-tasks
  • Syntax errors in imported files are caught before execution
  • Variables are resolved at parse time (static values)
  • Cannot be used with loops

Task File Structure

Task files contain only tasks – no play-level attributes like hosts, become, or vars.

tasks/install_apache.yml 
---
# Task file - contains only tasks, no play attributes

- name: Install Apache web server
  ansible.builtin.dnf:
    name: httpd
    state: present

- name: Copy Apache configuration
  ansible.builtin.template:
    src: httpd.conf.j2
    dest: /etc/httpd/conf/httpd.conf
  notify: Restart Apache

- name: Start and enable Apache
  ansible.builtin.service:
    name: httpd
    state: started
    enabled: true

Using import_tasks in a Playbook

main.yml 
---
- name: Configure web servers
  hosts: webservers
  become: true

  handlers:
    - name: Restart Apache
      ansible.builtin.service:
        name: httpd
        state: restarted

  tasks:
    - name: Import Apache installation tasks
      ansible.builtin.import_tasks:
        file: tasks/install_apache.yml

    - name: Import firewall configuration
      ansible.builtin.import_tasks:
        file: tasks/configure_firewall.yml

Conditional Imports

When you use when with import_tasks, the condition is applied to each imported task individually, not to the import itself.

Conditional Import 
tasks:
  - name: Import RHEL-specific tasks
    ansible.builtin.import_tasks:
      file: tasks/rhel_config.yml
    when: ansible_facts['os_family'] == 'RedHat'
⚠️ Condition Behavior

With import_tasks, the when condition is copied to every task in the imported file. This means each task is evaluated independently.

Including Task Files

Use include_tasks to dynamically load task files at runtime, enabling loops, variable filenames, and conditional loading.

Understanding include_tasks

The include_tasksDynamically includes tasks from an external file at runtime. The tasks are processed when the include_tasks task is executed, not at parse time. module loads task files when the task is reached during execution. This provides greater flexibility:

  • Can use loops to include multiple files
  • Can use variables in the filename
  • Conditions are evaluated once for the include
  • Tasks are NOT visible in --list-tasks

Using Loops with include_tasks

One of the most powerful features of include_tasks is the ability to use loops:

Include with Loop 
---
- name: Configure multiple services
  hosts: servers
  become: true
  vars:
    services:
      - apache
      - mysql
      - php

  tasks:
    - name: Include service configuration tasks
      ansible.builtin.include_tasks:
        file: "tasks/{{ item }}.yml"
      loop: "{{ services }}"

Variable Filenames

Include tasks based on facts or variables for dynamic, adaptive playbooks:

OS-Specific Includes 
tasks:
  - name: Include OS-specific tasks
    ansible.builtin.include_tasks:
      file: "tasks/{{ ansible_facts['os_family'] }}.yml"

  # This will include:
  # - tasks/RedHat.yml on RHEL/CentOS/Fedora
  # - tasks/Debian.yml on Debian/Ubuntu
💡 Loop Behavior

When using a loop, include_tasks includes the file once for each item. All tasks in the included file are executed before moving to the next loop iteration.

Import vs Include: Making the Right Choice

Understanding when to use static imports versus dynamic includes is key to building efficient, maintainable automation.

Feature Comparison

Feature import_tasks (Static) include_tasks (Dynamic)
Processing Time Parse time (before execution) Runtime (when task is reached)
--list-tasks Visibility ✅ Shows all imported tasks ❌ Shows only include statement
Loop Support ❌ Not supported ✅ Fully supported
Variable Filename ⚠️ Limited (parse-time values) ✅ Full runtime variables
when Behavior Applied to each task Applied once to include
Syntax Validation ✅ Early (parse time) ❌ Late (runtime)

Decision Guide

When to Use Each Method
Use Import
  • Tasks should be visible in --list-tasks
  • You need early syntax validation
  • Task file is always executed (no loops needed)
  • Handlers need to be triggered reliably
  • You want tags applied to all tasks
Use Include
  • You need to use loops
  • Filename depends on runtime variables
  • Tasks might be conditionally skipped entirely
  • Loading tasks based on gathered facts
  • Maximum flexibility is required
📖 Best Practice

Use import_tasks as your default choice for straightforward task organization. Switch to include_tasks only when you need its dynamic capabilities (loops, variable filenames, or runtime conditions).

Host and Group Variables

Organize variables efficiently using dedicated directories for host-specific and group-specific configurations.

Variable File Organization

Ansible automatically loads variables from special directories named group_varsA directory containing variable files that apply to hosts based on their group membership. Files are named after the group they apply to. and host_varsA directory containing variable files that apply to specific individual hosts. Files are named after the hostname.. These directories can be located adjacent to your inventory file or playbook.

project/
├── ansible.cfg
├── inventory
├── group_vars/
│ ├── all.yml # Variables for all hosts
│ ├── webservers.yml # Variables for webservers group
│ └── dbservers.yml # Variables for dbservers group
├── host_vars/
│ ├── web1.example.com.yml # Variables for specific host
│ └── db1.example.com.yml
└── site.yml

group_vars Directory

Files in group_vars/ are automatically loaded based on group membership:

group_vars/all.yml 
---
# Variables applied to ALL hosts
ntp_server: time.example.com
dns_servers:
  - 192.168.1.10
  - 192.168.1.11
timezone: America/New_York
admin_email: admin@example.com
group_vars/webservers.yml 
---
# Variables for hosts in the webservers group
http_port: 80
https_port: 443
web_root: /var/www/html
max_clients: 200
web_packages:
  - httpd
  - mod_ssl
  - php

host_vars Directory

Files in host_vars/ provide host-specific overrides:

host_vars/web1.example.com.yml 
---
# Variables specific to web1.example.com
max_clients: 500  # Override group default
ssl_certificate: /etc/pki/tls/certs/web1.crt
ssl_key: /etc/pki/tls/private/web1.key
vhosts:
  - name: main.example.com
    docroot: /var/www/main
  - name: api.example.com
    docroot: /var/www/api

Variable Precedence

When the same variable is defined in multiple places, Ansible uses a precedence order:

Variable Precedence (Highest to Lowest)
Highest Priority
Extra vars (-e)
↓
Play Level
Play vars, vars_files, vars_prompt
↓
Host Specific
host_vars/*
↓
Group Specific
group_vars/*
↓
Lowest Priority
group_vars/all

Using Subdirectories

For complex configurations, you can use subdirectories instead of single files:

group_vars/
├── webservers/ # Directory instead of file
│ ├── vars.yml # Main variables
│ └── vault.yml # Encrypted secrets
└── dbservers/
├── vars.yml
└── vault.yml
💡 Vault Integration

Using subdirectories allows you to keep sensitive data in encrypted vault.yml files while keeping regular variables in plain vars.yml files. Ansible loads all files in the directory automatically.
