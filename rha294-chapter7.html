Describing Role Structure

An Ansible role is defined by a standardized structure of subdirectories and files that makes your automation code reusable and shareable.

Structuring Ansible Playbooks with Roles

As you develop more playbooks, you are likely to discover that you have many opportunities to reuse code from playbooks that you wrote previously. Perhaps you could repurpose a play to configure a MySQL database for one application to configure a MySQL database for another application, with different hostnames, passwords, and users.

Ansible rolesA standardized way to organize Ansible code including tasks, handlers, variables, files, templates, and metadata into a reusable package that can be shared across projects. make it easier to reuse Ansible code generically. You can package all the tasks, variables, files, templates, and other resources needed to provision infrastructure or deploy applications in a standardized directory structure.

Benefits of Ansible Roles

♻️
Group Content Together
Roles group related content, enabling easy sharing of code with others in your organization or the community.
🖥️
Define System Types
Roles can define the essential elements of a system type, such as a web server, database server, or Git repository.
📊
Manageability
Roles make larger projects more manageable by breaking automation into smaller, focused units.
👥
Parallel Development
Roles can be developed in parallel by different users, enabling team collaboration on large automation projects.

Examining the Ansible Role Structure

The top-level directory defines the name of the role itself. Files are organized into subdirectories that are named according to each file's purpose in the role, such as tasks and handlers.

user.example/
├── defaults/ ← Default variable values (lowest precedence)
│ └── main.yml
├── files/ ← Static files for the copy module
├── handlers/ ← Handler definitions
│ └── main.yml
├── meta/ ← Role metadata and dependencies
│ └── main.yml
├── README.md ← Documentation
├── tasks/ ← Required: main.yml entry point
│ └── main.yml
├── templates/ ← Jinja2 templates
├── tests/ ← Test playbook and inventory
│ ├── inventory
│ └── test.yml
└── vars/ ← Role variables (higher precedence)
└── main.yml

Role Subdirectory Functions

Subdirectory Function
defaults/ Contains default values of role variables that can be overwritten when the role is used. These variables have low precedence and are intended to be changed and customized in plays.
files/ Contains static files that are referenced by role tasks using the copy module.
handlers/ Contains the role's handler definitions that can be triggered by tasks.
meta/ Contains information about the role, including author, license, platforms, and optional role dependencies.
tasks/ Contains the role's task definitions. The main.yml file is the entry point.
templates/ Contains Jinja2 templates that are referenced by role tasks using the template module.
tests/ Contains an inventory and test.yml playbook that can be used to test the role.
vars/ Contains role variable values with high precedence. These are intended for internal purposes within the role.
⚠️ Important

Not every role has all of these directories. Only the tasks/ directory with a main.yml file is required for a minimal role. All other directories are optional and created as needed for your automation requirements.

Using Ansible Roles in a Play

There are several ways to call roles in a play. Understanding these methods helps you choose the right approach for your automation needs.

Including and Importing Roles as Tasks

Roles can be added to a play by using an ordinary task. Use the ansible.builtin.import_role module to statically import a role, and the ansible.builtin.include_role module to dynamically include a role.

Importing a Role as a Task 
- name: Run a role as a task
  hosts: remote.example.com
  tasks:
    - name: A normal task
      ansible.builtin.debug:
        msg: 'first task'

    - name: A task to import role2 here
      ansible.builtin.import_role:
        name: role2

import_role vs include_role

Feature import_role (Static) include_role (Dynamic)
Processing Time When playbook is parsed When playbook is running
Variables Exposed to entire play Not exposed to rest of play
Conditionals/Loops Applied to each imported task Applied to include statement

Using a Roles Section in a Play

Another way you can call roles in a play is to list them in a roles sectionA section in an Ansible play that lists roles to be executed before any tasks in the play. Roles run in the order they are listed.. The roles section is similar to the tasks section, except it consists of a list of roles instead of tasks.

Using the roles Section 
- name: A play that runs roles
  hosts: remote.example.com
  roles:
    - role: role1
    - role: role2
      var1: val1
      var2: val2
🔄 Execution Order

When you use a roles section, the roles run first, before any tasks that you define for that play. Whether the roles section is listed before or after the tasks section in the play does not matter.

Special Tasks Sections

There are two special task sections that can be used with roles: pre_tasks and post_tasks.

Execution Order with pre_tasks and post_tasks 
- name: Play to illustrate order of execution
  hosts: remote.example.com
  pre_tasks:    # 1. Runs first
    - name: This task runs first
      ansible.builtin.debug:
        msg: This task is in pre_tasks
  roles:        # 2. Roles run second
    - role: role1
  tasks:        # 3. Tasks run third
    - name: This task runs after roles
      ansible.builtin.debug:
        msg: This task is in tasks
  post_tasks:   # 4. Runs last
    - name: This task runs last
      ansible.builtin.debug:
        msg: This task is in post_tasks
💡 Best Practice

In general, if you think you need pre_tasks and post_tasks sections in your play because you are using roles, consider importing the roles as tasks and including only a tasks section. Alternatively, it might be simpler to have multiple plays in your playbook.

Creating Roles

Learn how to create roles using ansible-galaxy and organize your automation content effectively.

The Role Creation Process

Creating roles in Ansible does not require any special development tools. Creating and using a role is a three-step process:

1️⃣
Create the Structure
Create the role directory structure using ansible-galaxy role init or manually.
2️⃣
Define the Content
Write the tasks, handlers, templates, and variables for your role.
3️⃣
Use the Role
Reference the role in a playbook using the roles section or import/include modules.

Creating a Role Skeleton

The ansible-galaxyA command-line tool for managing Ansible roles and collections. It can create role skeletons, install roles from Galaxy, and manage dependencies. command creates a complete role skeleton with all standard directories:

Creating a Role with ansible-galaxy 
# Navigate to the roles directory
[user@host playbook-project]$ cd roles

# Create a new role skeleton
[user@host roles]$ ansible-galaxy role init my_new_role
- Role my_new_role was created successfully

# View the created structure
[user@host roles]$ ls my_new_role/
defaults  files  handlers  meta  README.md  tasks  templates  tests  vars

Defining the Role Content

After creating the directory structure, you must write the content of the role. A good place to start is the ROLENAME/tasks/main.yml task file, which is the main list of tasks that the role runs.

Example: roles/motd/tasks/main.yml 
# tasks file for motd

- name: deliver motd file
  ansible.builtin.template:
    src: motd.j2
    dest: /etc/motd
    owner: root
    group: root
    mode: '0444'

Recommended Practices for Role Development

💡 Best Practices
  • Maintain each role in its own version control repository
  • Use variables to configure roles so you can reuse them in different scenarios
  • Avoid storing sensitive information (passwords, SSH keys) directly in the role
  • Use ansible-galaxy role init to start your role, then remove unnecessary files
  • Create and maintain README.md and meta/main.yml files to document the role
  • Keep your role focused on a specific purpose or function
⚠️ Security Note

Roles should not have site-specific data in them or contain any secrets like passwords or private keys because roles are supposed to be generic, reusable, and freely shareable. Secrets should be provided to the role through other means, such as Ansible Vault encrypted files.

Role Variables and Precedence

Understanding how role variables work and their precedence is crucial for creating flexible, reusable roles.

Defining Variables and Defaults

Role variables are defined in vars/main.yml with high precedence — they cannot be easily overridden by inventory variables or play variables. These are used for the internal functioning of the role.

Default variables are defined in defaults/main.yml with low precedence — they can be overridden by any other variable. These provide the person writing a play with a way to customize the role's behavior.

Example: roles/motd/defaults/main.yml 
# Default variable values (easily overridden)
system_owner: user@host.example.com

Variable Precedence

The value of any variable defined in a role's defaults directory is overwritten if that same variable is defined:

  • In an inventory file (host variable or group variable)
  • In a YAML file under group_vars or host_vars directories
  • As a variable nested in the vars keyword of a play
  • As a variable when including the role in the roles keyword of a play
Overriding Role Variables in a Playbook 
- name: use motd role playbook
  hosts: remote.example.com
  remote_user: devops
  become: true
  roles:
    - role: motd
      system_owner: someone@host.example.com  # Overrides default
📌 Variable Precedence Summary
  • defaults/ variables: Lowest precedence, easily overridden
  • vars/ variables: High precedence, difficult to override
  • Role parameters (inline): Highest precedence for roles

Role Dependencies

Role dependencies allow a role to include other roles as dependencies. Dependencies are defined in the meta/main.yml file.

Example: meta/main.yml with Dependencies 
dependencies:
  - role: apache
    port: 8080
  - role: postgres
    dbname: serverlist
    admin_user: felix

Deploying Roles from External Content Sources

If you are using roles in your Ansible Playbooks, you should get those roles from a centrally managed source to ensure consistency across projects.

External Content Sources

Roles can come from several external sources:

📦
Git Repositories
Private content stored in Git repositories managed by your organization, accessible via HTTPS or SSH.
🌐
Ansible Galaxy
Community-maintained roles available at galaxy.ansible.com. Not officially supported by Red Hat.
🏢
Automation Hub
Red Hat Certified Content Collections for Ansible Automation Platform subscribers.
📁
Tar Archives
Roles distributed as tar archive files from websites or internal servers.

Introducing Ansible Galaxy

A public library of Ansible content written by a variety of Ansible administrators and users is available at Ansible GalaxyA website (galaxy.ansible.com) hosting community-contributed Ansible roles and collections. Content is not supported by Red Hat.. This library contains thousands of Ansible roles with a searchable database.

ansible-galaxy role Commands 
# Search for roles
[user@host ~]$ ansible-galaxy role search 'redis' --platforms EL

# Get information about a role
[user@host ~]$ ansible-galaxy role info geerlingguy.redis

# Install a role
[user@host ~]$ ansible-galaxy role install geerlingguy.redis -p roles

# List installed roles
[user@host ~]$ ansible-galaxy role list -p roles

# Remove a role
[user@host ~]$ ansible-galaxy role remove nginx
⚠️ Community Content Warning

Roles from Ansible Galaxy are not supported by Red Hat, nor does Red Hat audit or review this code. Volunteers in the Ansible community maintain this site. Use these roles at your own risk.

Installing Roles Using a Requirements File

If you have a playbook that requires specific roles, create a requirements file to manage dependencies.

Creating a Requirements File

Create a roles/requirements.yml file in your project directory that specifies which roles are needed. This acts as a dependency manifest for your playbook project.

Example: roles/requirements.yml 
# From a Git repository
- src: https://git.example.com/someuser/someuser.myrole
  scm: git
  version: "1.5.0"

# From Ansible Galaxy
- src: geerlingguy.redis
  version: "1.5.0"
  name: redis_prod

# From a Git repository using SSH
- src: git@github.com/geerlingguy/ansible-role-nginx.git
  scm: git
  version: master
  name: nginx

# From a tar archive file
- src: file:///opt/local/roles/myrole.tar
  name: myrole

Requirements File Attributes

Attribute Description
src The source of the role: Ansible Galaxy role name, URL for Git repository, or path to tar file
scm Required for Git repositories. Set to git
version Branch name, tag, or commit hash. Defaults to latest commit on default branch
name Override the local name of the role

Installing Roles from Requirements

Installing Roles 
# Install roles from requirements file into roles/ directory
[user@host project]$ ansible-galaxy role install \
  -r roles/requirements.yml \
  -p roles

Starting galaxy role install process
- downloading role from https://git.example.com/someuser/someuser.myrole
- extracting myrole to /home/user/project/roles/someuser.myrole
- someuser.myrole (1.5.0) was installed successfully
📌 Version Pinning

Specify the version of the role in your requirements.yml file, especially for playbooks in production. If you do not specify a version, you get the latest version of the role, which might cause compatibility issues if the upstream author makes changes.

Getting Roles and Modules from Content Collections

Ansible Content Collections provide a way to package and distribute modules, roles, and plugins independently of Ansible Core.

Ansible Content Collections

With Ansible Content CollectionsA distribution format for Ansible content including modules, roles, plugins, and documentation. Collections can be versioned and distributed independently of Ansible Core., Ansible code updates are separated from updates to modules and plug-ins. This enables vendors and developers to maintain and distribute their collections at their own pace, independently of Ansible releases.

🔌
redhat.insights
Provides modules and roles to register systems with Red Hat Insights for RHEL.
🌐
cisco.ios
Supported by Cisco, provides modules and plug-ins to manage Cisco IOS network appliances.
🔐
community.crypto
Community collection providing modules to create SSL/TLS certificates.

Namespaces for Collections

Collection names are organized into namespacesThe first part of a collection name that identifies the vendor, partner, or organization. Examples: community, redhat, cisco. to avoid naming conflicts. The namespace is the first part of a collection name.

Namespace Example Collections Maintained By
community community.crypto, community.postgresql, community.rabbitmq Ansible Community
redhat redhat.rhv, redhat.satellite, redhat.insights Red Hat
cisco cisco.ios, cisco.nxos, cisco.aci Cisco
ansible ansible.builtin, ansible.posix, ansible.netcommon Ansible Core Team

Sources of Collections

🏢
Automation Hub
Red Hat Certified Content Collections with support from Red Hat and ecosystem partners. Requires Ansible Automation Platform subscription.
🔒
Private Automation Hub
Your organization's on-site hub for distributing private collections. Included with Red Hat Ansible Automation Platform.
🌌
Ansible Galaxy
Community-supported collections at galaxy.ansible.com. No formal support guarantees.

Using Ansible Content Collections

Learn how to install and use content from Ansible Content Collections in your playbooks.

Installing Collections with Requirements File

Create a collections/requirements.yml file to specify the collections your project needs.

Example: collections/requirements.yml 
collections:
  # From configured sources (automation hub/galaxy)
  - name: community.crypto

  # Specific version
  - name: ansible.posix
    version: "1.2.0"

  # From local tar archive
  - name: /tmp/community-dns-1.2.0.tar.gz

  # From URL
  - name: http://www.example.com/redhat-insights-1.0.5.tar.gz

  # From Git repository
  - name: git+https://github.com/ansible-collections/community.general.git
    version: main

Installing Collections

Installing Collections 
# Install collections from requirements file
[user@host project]$ ansible-galaxy collection install \
  -r collections/requirements.yml \
  -p collections

# List installed collections
[user@host project]$ ansible-galaxy collection list -p collections

# View collections in ansible-navigator
[user@host project]$ ansible-navigator collections

Using Collections in Playbooks

Reference modules and roles from collections using their Fully Qualified Collection Name (FQCN)The complete name of a module or role in a collection, in the format namespace.collection.name. Example: community.mysql.mysql_user.

Using a Module from a Collection 
- name: Create database user
  hosts: db.example.com
  tasks:
    - name: Ensure the operator1 database user is defined
      community.mysql.mysql_user:  # FQCN
        name: operator1
        password: Secret0451
        priv: '*.*:ALL'
        state: present
Using a Role from a Collection 
- name: Configure Red Hat Satellite organizations
  hosts: localhost
  tasks:
    - name: Ensure the organizations exist
      ansible.builtin.include_role:
        name: redhat.satellite.organizations  # FQCN
      vars:
        satellite_server_url: https://sat.example.com
        satellite_username: admin
        satellite_password: Sup3r53cr3t

Reusing Content with System Roles

System roles are a set of Ansible roles you can use to configure and manage various components of Red Hat Enterprise Linux.

What are System Roles?

System rolesA set of Ansible roles provided by Red Hat for configuring common RHEL system components like networking, time synchronization, and SELinux. provide automation for many common system configuration tasks, including time synchronization, networking, firewall, tuning, and logging.

These roles are intended to provide an automation API that is consistent across multiple major and minor releases of Red Hat Enterprise Linux.

Benefits of System Roles

🔄
Cross-Version Compatibility
Configure RHEL 6, 7, 8, and 9 systems with the same role variables, regardless of underlying service differences.
✅
Supported by Red Hat
Available through automation hub for AAP subscribers or as the rhel-system-roles RPM package.
📚
Well Documented
Comprehensive documentation available via ansible-navigator and the Red Hat Customer Portal.

Available System Roles

Role Purpose
redhat.rhel_system_roles.timesync Configure time synchronization using chrony or NTP
redhat.rhel_system_roles.selinux Configure SELinux mode, booleans, file contexts, and ports
redhat.rhel_system_roles.network Configure network interfaces and connections
redhat.rhel_system_roles.firewall Configure firewalld rules and zones
redhat.rhel_system_roles.storage Configure storage volumes and file systems
redhat.rhel_system_roles.logging Configure system logging
redhat.rhel_system_roles.kdump Configure kernel crash dump

System Role Examples

See how system roles simplify common configuration tasks across RHEL systems.

Example: Time Synchronization Role

The redhat.rhel_system_roles.timesync role configures NTP time synchronization. It automatically uses the appropriate service (chronyd for RHEL 9, ntpd for RHEL 6).

Configuring Time Synchronization 
- name: Time Synchronization Play
  hosts: webservers
  vars:
    timesync_ntp_servers:
      - hostname: 0.rhel.pool.ntp.org
        iburst: yes
      - hostname: 1.rhel.pool.ntp.org
        iburst: yes
      - hostname: 2.rhel.pool.ntp.org
        iburst: yes
  roles:
    - redhat.rhel_system_roles.timesync

Example: SELinux Role

The redhat.rhel_system_roles.selinux role manages SELinux configuration including mode, booleans, file contexts, and port labels.

Configuring SELinux 
# SELinux role variables
selinux_state: enforcing

selinux_booleans:
  - name: 'httpd_enable_homedirs'
    state: 'on'
    persistent: 'yes'

selinux_fcontexts:
  - target: '/srv/www(/.*)?'
    setype: 'httpd_sys_content_t'
    state: 'present'

selinux_ports:
  - ports: '82'
    setype: 'http_port_t'
    proto: 'tcp'
    state: 'present'
⚠️ SELinux Role Reboot Handling

The SELinux role may require a reboot to complete changes. It sets selinux_reboot_required to true and fails if a reboot is needed. Use a block/rescue structure to handle this:

Handling SELinux Reboots 
- name: Apply SELinux role
  block:
    - ansible.builtin.include_role:
        name: redhat.rhel_system_roles.selinux
  rescue:
    - name: Check for failure for other reasons
      ansible.builtin.fail:
      when: not selinux_reboot_required

    - name: Restart managed host
      ansible.builtin.reboot:

    - name: Reapply SELinux role
      ansible.builtin.include_role:
        name: redhat.rhel_system_roles.selinux

Content Collections
Collections bundle modules, roles, and plugins for independent distribution. Use FQCN to reference content from collections.

Command Reference

Command Purpose
ansible-galaxy role init ROLE Create a new role skeleton
ansible-galaxy role install -r requirements.yml -p roles Install roles from requirements file
ansible-galaxy role list -p roles List installed roles
ansible-galaxy collection install -r requirements.yml -p collections Install collections from requirements file
ansible-galaxy collection list List installed collections
ansible-navigator collections Browse collections interactively
