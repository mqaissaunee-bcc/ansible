Introduction to Ansible Roles

Roles help you organize and reuse Ansible automation content using a standardized file structure.

Why Use Roles?

As your Ansible projects grow, playbooks can become large and difficult to maintain. Roles solve this by:

  • Simplifying playbooks - Group related tasks, variables, files, templates, and handlers together
  • Enabling reuse - Write automation once, use it in multiple playbooks and projects
  • Sharing code - Roles can be shared via Ansible Galaxy or private repositories
  • Standardizing structure - Consistent organization makes code easier to understand
💡 Best Practice

Start creating roles early in your automation journey. Even simple roles help establish good habits and make your code more maintainable as projects grow.

What is a Role?

An Ansible roleA standardized directory structure containing Ansible content (tasks, handlers, variables, templates, files) that can be reused across playbooks and shared with others. is a standardized directory structure containing:

  • Tasks - The main list of actions the role performs
  • Handlers - Tasks triggered by notifications from other tasks
  • Variables - Default values and internal variables for the role
  • Templates - Jinja2 template files that can use variables
  • Files - Static files to deploy to managed hosts
  • Metadata - Information about the role (author, dependencies, etc.)

Role Directory Structure

Roles use a standardized directory structure that Ansible automatically recognizes.

Standard Role Layout

A role is defined by a directory with a specific structure. Ansible looks for roles in the roles/ subdirectory of your project:

roles/
└── myrole/ # Role name = directory name
├── defaults/ # Low-precedence default variables
│ └── main.yml
├── vars/ # High-precedence internal variables
│ └── main.yml
├── tasks/ # Main task list (required)
│ └── main.yml
├── handlers/ # Handler definitions
│ └── main.yml
├── templates/ # Jinja2 template files
├── files/ # Static files to deploy
├── meta/ # Role metadata and dependencies
│ └── main.yml
└── README.md # Documentation

Directory Purposes

DirectoryPurposeKey File
tasks/Contains the main task list for the rolemain.yml
handlers/Handler definitions triggered by notifymain.yml
defaults/Default variable values (low precedence)main.yml
vars/Internal role variables (high precedence)main.yml
files/Static files referenced by tasksAny files
templates/Jinja2 templates for the template module*.j2 files
meta/Role metadata, author info, dependenciesmain.yml
ℹ️ Minimal Role

At minimum, a role only needs a tasks/main.yml file. All other directories are optional and only needed if you use those features.

Creating a Role Skeleton

Use ansible-galaxy role init to create the standard directory structure:

Creating a new role
# Create a new role called "myvhost"
$ cd ~/project
$ ansible-galaxy role init roles/myvhost

# View the created structure
$ tree roles/myvhost
roles/myvhost/
├── defaults/
│   └── main.yml
├── handlers/
│   └── main.yml
├── meta/
│   └── main.yml
├── README.md
├── tasks/
│   └── main.yml
├── templates/
├── tests/
│   ├── inventory
│   └── test.yml
└── vars/
    └── main.yml

Role Variables

Understanding variable precedence in roles is crucial for writing flexible, reusable automation.

Two Types of Role Variables

Roles have two directories for variables with different precedence levels:

Low Precedence defaults/

Variables meant to be customized by users of the role.

  • Easily overridden by almost any other variable
  • Good for user-configurable options
  • Document in README for role users
  • Example: http_port: 80
High Precedence vars/

Variables internal to the role that should not change.

  • Hard to override - use for constants
  • Good for role-internal values
  • Not intended for user customization
  • Example: config_file: /etc/app/app.conf
⚠️ Important Distinction

Role parameters (set when calling the role) have the highest precedence and override both defaults/ and vars/ variables. This lets users customize any aspect of a role when needed.

Example: MOTD Role

roles/motd/defaults/main.yml
# Default values - users should customize these
system_owner: "Example Corp"
support_email: "support@example.com"
roles/motd/tasks/main.yml
- name: Deploy MOTD template
  ansible.builtin.template:
    src: motd.j2
    dest: /etc/motd
    owner: root
    group: root
    mode: '0644'
roles/motd/templates/motd.j2
This system is managed by {{ system_owner }}.
For support, contact: {{ support_email }}

Using Roles in Playbooks

There are multiple ways to include roles in your playbooks, each with different use cases.

The roles Section

The simplest way to use roles is with the roles keyword in a play:

site.yml - Using the roles section
- name: Configure web servers
  hosts: webservers

  roles:
    # Simple reference (uses defaults)
    - myvhost

    # With role parameters (override defaults)
    - role: myvhost
      vhost_name: "example.com"
      vhost_port: 8080

Import vs Include

You can also use roles as tasks with import_role or include_role:

Static import - processed at parse time
tasks:
  - name: Import the myvhost role
    ansible.builtin.import_role:
      name: myvhost
    vars:
      vhost_name: "example.com"

Use when: Role content is static and known at playbook parse time. Handlers are available immediately.

Dynamic include - processed at runtime
tasks:
  - name: Include role based on variable
    ansible.builtin.include_role:
      name: "{{ role_name }}"
    when: some_condition

Use when: Role selection depends on variables or conditionals evaluated at runtime.

Play Execution Order

Understanding when roles, tasks, and handlers execute is essential for complex playbooks.

Standard Execution Order

When a play has multiple sections, they execute in this order:

Step 1
pre_tasks
↓
Step 2
handlers (notified by pre_tasks)
↓
Step 3
roles
↓
Step 4
tasks
↓
Step 5
handlers (notified by roles/tasks)
↓
Step 6
post_tasks
↓
Step 7
handlers (notified by post_tasks)
⚠️ Key Insight

Roles always run before tasks! The order in your playbook file doesn't change this. If you need tasks to run before roles, put them in pre_tasks.

Example Playbook

Complete execution order example
- name: Demonstrate execution order
  hosts: servers

  pre_tasks:
    - name: Pre-task runs first
      ansible.builtin.debug:
        msg: "1. This runs before anything else"
      notify: my_handler

  roles:
    - myrole  # 3. Roles run after pre_tasks handlers

  tasks:
    - name: Regular task
      ansible.builtin.debug:
        msg: "4. This runs after roles"

  post_tasks:
    - name: Post-task runs last
      ansible.builtin.debug:
        msg: "6. This runs after all tasks"

  handlers:
    - name: my_handler
      ansible.builtin.debug:
        msg: "2. Handler runs after pre_tasks"

Reusing Content from External Sources

Install and manage roles from Ansible Galaxy, Git repositories, and other sources.

Role Sources

Ansible can install roles from multiple sources:

  • Ansible Galaxy - Community role repository at galaxy.ansible.com
  • Git repositories - GitHub, GitLab, or private Git servers
  • Tar archives - Downloaded from URLs or local files
  • Red Hat automation hub - Certified content at console.redhat.com

Requirements File

The best practice is to define role dependencies in a requirements.ymlA YAML file that lists roles and collections to install, including their sources and versions. Located in the roles/ directory. file:

roles/requirements.yml
# From Ansible Galaxy
- name: geerlingguy.docker
  version: "6.1.0"

# From a Git repository
- name: my-custom-role
  src: git@github.com:example/ansible-role.git
  scm: git
  version: v1.2.0

# From a tar archive URL
- name: webserver
  src: https://example.com/roles/webserver.tar.gz
⚠️ Always Specify Versions

Without a version, you get the latest code which may have breaking changes. Always pin versions for reproducible automation.

Installing Roles

ansible-galaxy role commands
# Install roles from requirements file
$ ansible-galaxy role install -r roles/requirements.yml -p roles

# Install a single role from Galaxy
$ ansible-galaxy role install geerlingguy.docker -p roles

# List installed roles
$ ansible-galaxy role list -p roles

# Remove a role
$ ansible-galaxy role remove geerlingguy.docker -p roles
💡 Project Directory

Always use -p roles to install roles into your project directory. This ensures they're available when using ansible-navigator with execution environments.

Ansible Content Collections

Collections package modules, roles, plugins, and documentation in a single distributable unit.

What is a Collection?

An Ansible Content CollectionA distribution format for Ansible content that includes modules, plugins, roles, and documentation. Collections use namespaced naming (namespace.collection). bundles related automation content together:

  • Modules - Task plugins that perform actions
  • Roles - Reusable automation packages
  • Plugins - Filters, callbacks, inventory plugins, etc.
  • Documentation - Usage guides and examples

Fully Qualified Collection Names (FQCN)

Collections use a FQCNFully Qualified Collection Name - the complete path to content within a collection in the format: namespace.collection.content_name to uniquely identify content:

ansible . builtin . copy
namespace collection module

Example FQCNs

FQCNTypeDescription
ansible.builtin.copyModuleCopy files to hosts
ansible.builtin.debugModulePrint debug messages
amazon.aws.ec2_instanceModuleManage EC2 instances
redhat.rhel_system_roles.timesyncRoleConfigure time sync

Collection Sources

🏢 Automation Hub

console.redhat.com

  • Red Hat Certified collections
  • Supported by Red Hat
  • Tested and validated
  • Requires subscription
🌐 Ansible Galaxy

galaxy.ansible.com

  • Community collections
  • Not supported by Red Hat
  • Variable quality
  • Free to use

Installing Collections

collections/requirements.yml
collections:
  - name: amazon.aws
    version: "6.0.0"
    source: https://galaxy.ansible.com

  - name: redhat.rhel_system_roles
    version: "1.21.0"
Installing collections
# Install from requirements file
$ ansible-galaxy collection install -r collections/requirements.yml -p collections

# List installed collections
$ ansible-galaxy collection list -p collections

# Browse with navigator
$ ansible-navigator collections

Red Hat System Roles

Configure RHEL subsystems consistently using Red Hat-supported system roles.

What are System Roles?

The redhat.rhel_system_roles collection provides roles for configuring common RHEL subsystems. These roles provide a stable, consistent API across multiple RHEL versions.

Available System Roles

RolePurpose
timesyncConfigure time synchronization (NTP/chrony)
selinuxManage SELinux mode and policies
firewallConfigure firewalld rules
networkConfigure network interfaces
storageManage disks, partitions, LVM
certificateManage TLS/SSL certificates
crypto_policiesConfigure system-wide crypto policies

Example: Time Synchronization

Configuring NTP with timesync role
- name: Configure time synchronization
  hosts: servers
  vars:
    timesync_ntp_servers:
      - hostname: time.example.com
        iburst: true
      - hostname: 0.rhel.pool.ntp.org
        iburst: true
  roles:
    - redhat.rhel_system_roles.timesync

Example: SELinux Configuration

The SELinux role may require a reboot if the mode changes. Use a block/rescue pattern:

SELinux with reboot handling
- name: Configure SELinux
  hosts: servers
  vars:
    selinux_state: enforcing
  tasks:
    - name: Apply SELinux configuration
      block:
        - name: Include SELinux role
          ansible.builtin.include_role:
            name: redhat.rhel_system_roles.selinux
      rescue:
        - name: Reboot if required
          ansible.builtin.reboot:
          when: selinux_reboot_required | bool

        - name: Re-apply SELinux role after reboot
          ansible.builtin.include_role:
            name: redhat.rhel_system_roles.selinux
💡 Documentation

Each system role includes detailed documentation. Check the role's README and the doc/ directory for configuration options and examples.

✓ Remember These Points

  • vars/ variables have high precedence (internal to the role)
