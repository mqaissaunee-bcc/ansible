Troubleshooting Playbooks

When an Ansible Playbook does not behave as expected, you need to troubleshoot its behavior. The ansible-navigator or ansible-playbook commands provide options to help troubleshoot playbooks.

Verbose Mode

Verbose modeA debugging feature that displays progressively more detailed information about playbook execution, from basic task results to full SSH connection details. provides progressively more detailed output about playbook execution, helping you understand exactly what Ansible is doing.

Verbosity Levels

The -v option provides additional debug output. You can specify up to four levels:

OptionDescription
-v Displays task results
-vv Displays task results and task configuration
-vvv Includes information about connections to managed hosts
-vvvv Adds extra verbosity options to the connection plug-ins, including users being used to run scripts on managed hosts and what scripts have been executed

Interactive Verbose Simulator

Select a verbosity level to see how the output changes:

Using Verbose Mode

Command line usage
# Basic verbose output with ansible-navigator
$ ansible-navigator run -m stdout playbook.yml -v

# Maximum verbosity for connection debugging
$ ansible-navigator run -m stdout playbook.yml -vvvv

# With ansible-playbook command
$ ansible-playbook playbook.yml -vvv
💡 Best Practice

Start with -v and increase verbosity only if needed. Level 4 (-vvvv) generates a lot of output and is best reserved for debugging complex connection issues.

The Debug Module

The ansible.builtin.debug module provides a way to print statements during playbook execution, which is useful for debugging variables without necessarily halting the playbook.

Basic Usage

Use the debug module to display messages or variable values during execution:

Debug module examples
tasks:
  # Display a simple message
  - name: Show greeting message
    ansible.builtin.debug:
      msg: "Hello from {{ inventory_hostname }}"

  # Display a variable value
  - name: Show ansible_facts
    ansible.builtin.debug:
      var: ansible_facts['os_family']

  # Display with controlled verbosity
  - name: Show debug info only with -vv
    ansible.builtin.debug:
      msg: "Detailed debug information"
      verbosity: 2

Debug Parameters

ParameterDescription
msg The customized message to print. If omitted, prints a generic message.
var A variable name to debug. Mutually exclusive with the msg option. Use without quotes or curly braces.
verbosity A number that controls when the debug is run, as the result of the -v option to playbook execution must be greater than or equal to this value for the debug to run.

Debugging Registered Variables

Use debug to inspect the structure of registered variablesVariables created using the register keyword that capture the output of a task, including stdout, stderr, return codes, and other metadata.:

Inspecting registered output
tasks:
  - name: Get service status
    ansible.builtin.command:
      cmd: systemctl status httpd
    register: service_result
    ignore_errors: true
    changed_when: false

  - name: Show full result structure
    ansible.builtin.debug:
      var: service_result

  - name: Show just the return code
    ansible.builtin.debug:
      msg: "Return code: {{ service_result.rc }}"

Interactive Debug Output Demo

Select debug type and click "Run Task" to see output...
⚠️ Important

The var parameter takes a variable name without quotes or curly braces. Using var: "{{ my_var }}" is incorrect and will cause unexpected results.

Syntax Checking

The --syntax-check option validates playbook syntax before execution, catching errors early without wasting time on failed runs.

The --syntax-check Option

Use --syntax-check to validate YAML structure and Ansible syntax without connecting to managed hosts:

Syntax check commands
# With ansible-navigator
$ ansible-navigator run -m stdout playbook.yml --syntax-check

# With ansible-playbook
$ ansible-playbook playbook.yml --syntax-check

# Successful output
playbook: /home/student/troubleshoot-playbook/playbook.yml

# Error output example
ERROR! We were unable to read either as JSON nor YAML, these are the errors we got from each:
Syntax Error while loading YAML.
  did not find expected '-' indicator
The error appears to be in '/home/student/troubleshoot-playbook/samba.yml': line 38

Common Syntax Errors

🔴 Indentation Errors ▼

YAML requires consistent spacing. The most common error is incorrect indentation.

Error Example
Syntax Error while loading YAML.
mapping values are not allowed in this context
The error appears to be in 'playbook.yml': line 5
Solution

Use 2 spaces per indentation level. Check that all items at the same level have identical indentation. Never use tabs.

🔴 Missing Quotes ▼

Values starting with {{ or containing special characters need quotes.

Wrong vs Correct
# Wrong - YAML syntax error
path: {{ doc_root }}/html

# Correct - quoted
path: "{{ doc_root }}/html"
Solution

Always quote values that start with {{ or contain colons, hashtags, or other special YAML characters.

🔴 Invalid Module Names ▼

Typos in module names or using deprecated names without the collection prefix.

Error Example
ERROR! couldn't resolve module/action 'coppy'
Solution

Use ansible-doc -l to list available modules. Always use FQCNs like ansible.builtin.copy.

Using ansible-lint

ansible-lintA linting tool that checks playbooks for best practices, deprecated syntax, and potential issues beyond basic syntax checking. goes beyond syntax checking to enforce best practices:

ansible-lint usage
# Run lint check
$ ansible-lint playbook.yml

# Example output
WARNING Listing 2 violation(s) that are fatal
playbook.yml:5 name[missing]: All tasks should be named.
playbook.yml:8 fqcn[action-core]: Use FQCN for builtin modules.

Check Mode and Diff

Preview changes before applying them with check mode (dry run) and see exactly what will change with diff mode.

Check Mode (Dry Run)

The --check option runs the playbook without making any changes. Tasks in a playbook run as they normally would, but rather than making changes to managed hosts, tasks report what changes would have been made.

Check mode commands
# Basic check mode with ansible-navigator
$ ansible-navigator run -m stdout playbook.yml --check

# Check mode with diff to see changes
$ ansible-navigator run -m stdout playbook.yml --check --diff

# Using ansible-playbook
$ ansible-playbook playbook.yml --check --diff
⚠️ Important Limitation

Check mode does not work well with tasks that require information from prior tasks. For example, a task that uses a registered variable from a previous ansible.builtin.command task may fail in check mode because the command did not actually run.

Diff Mode

The --diff option shows changes made to template files on managed hosts:

Diff output example
TASK [Configure Apache] **************************
--- before: /etc/httpd/conf/httpd.conf
+++ after: /home/student/.ansible/tmp/httpd.conf
- ServerAdmin root@localhost
+ ServerAdmin admin@example.com

Forcing Tasks in Check Mode

Some tasks must always run, even in check mode. Use check_mode: false to force execution:

Force task execution in check mode
- name: This task always runs, even in check mode
  ansible.builtin.command:
    cmd: cat /etc/passwd
  check_mode: false
  register: passwd_contents
  changed_when: false

Conditional Execution Based on Check Mode

Use the ansible_check_mode variable to run tasks only in check mode or only in normal mode:

Using ansible_check_mode variable
- name: Run only in check mode
  ansible.builtin.debug:
    msg: "This only runs during check mode"
  when: ansible_check_mode

- name: Skip during check mode
  ansible.builtin.service:
    name: httpd
    state: restarted
  when: not ansible_check_mode

Start-at-Task and Step Mode

Additional options to control task execution during troubleshooting:

Targeted execution
# Start from a specific task
$ ansible-playbook playbook.yml --start-at-task="Install packages"

# Step through tasks one at a time (interactive)
$ ansible-playbook playbook.yml --step

# List all tasks without running
$ ansible-playbook playbook.yml --list-tasks

# List target hosts without running
$ ansible-playbook playbook.yml --list-hosts
💡 Pro Tip

The --step option prompts you before each task with (N)o/(y)es/(c)ontinue options. This is extremely useful for debugging complex playbooks.

Troubleshooting Ansible Managed Hosts

When managed hosts fail to respond to Ansible commands, you need to troubleshoot the connections to those hosts. This section covers common connection problems and their solutions.

Testing Managed Hosts Using Ad Hoc Commands

A good approach to test a managed host is to use an ad hoc command. If you can successfully connect with an ad hoc command, then you know that the control node has network connectivity to the managed host and has been successfully authenticated.

Testing connectivity
# Test connection to all hosts
$ ansible all -m ansible.builtin.ping

# Test specific group with verbose output
$ ansible webservers -m ansible.builtin.ping -vvvv

Common Connection Errors

UNREACHABLE Error
TASK [Gathering Facts] *********************************
fatal: [host.example.com]: UNREACHABLE! => {"changed": false,
"msg": "Failed to connect to the host via ssh: Permission denied
(publickey,gssapi-keyex,gssapi-with-mic,password).",
"unreachable": true}

Connection Troubleshooting Checklist

1
Verify Basic Connectivity
ping hostname - Ensure network connectivity exists
ssh user@hostname - Test SSH connection manually
2
Check remote_user Setting
Verify remote_user in ansible.cfg or playbook matches a valid user on the managed host.
3
Validate SSH Keys
ssh-add -l - Check if SSH agent has your key
Verify public key is in ~/.ssh/authorized_keys on the managed host
4
Check Inventory Variables
Look for ansible_host, ansible_user, ansible_ssh_private_key_file overrides
5
Use Maximum Verbosity
ansible-playbook playbook.yml -vvvv - Shows full SSH connection details

Important Connection Variables

VariableDescription
ansible_hostThe IP address or hostname to connect to (overrides inventory name)
ansible_userThe user to connect as on the managed host
ansible_ssh_private_key_filePath to the private SSH key file
ansible_portSSH port number (default: 22)
ansible_connectionConnection type (ssh, local, etc.)
⚠️ Common Mistake

Setting ansible_host to the wrong IP address is a common source of connection failures. Always verify that inventory host names resolve correctly or that ansible_host is set to the correct IP.

Privilege Escalation Issues

Many tasks require root privileges. Learn to troubleshoot privilege escalationThe process of gaining elevated permissions (typically root) to perform administrative tasks. Ansible uses 'become' to implement sudo, su, or other escalation methods. problems with the become directive.

Common Privilege Escalation Errors

sudo password required
TASK [Install httpd] ***********************************
fatal: [server1]: FAILED! => {"msg": "Missing sudo password"}

Become Configuration

If your playbook connects as a remote_user and then uses privilege escalation to become the root user (or some other user), make sure that become is set properly, and that you are using the correct value for the become_user directive.

ansible.cfg become settings
# ansible.cfg
[privilege_escalation]
become = true
become_method = sudo
become_user = root
become_ask_pass = false

Playbook-Level Become

Using become in playbooks
---
- name: Configure web server
  hosts: webservers
  become: true              # Enable privilege escalation
  become_method: sudo      # Method (sudo, su, pbrun, etc.)
  become_user: root        # Target user

  tasks:
    - name: Install packages (requires root)
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Run as specific user
      ansible.builtin.command:
        cmd: whoami
      become_user: apache    # Override for this task

Troubleshooting Steps

1
Verify sudo Configuration
Check /etc/sudoers or files in /etc/sudoers.d/ on the managed host to ensure the remote user can use sudo without a password (NOPASSWD option).
2
Check become Settings
Verify become: true is set in the playbook or ansible.cfg. Check that become_user is set to the correct target user (usually root).
3
Test sudo Manually
SSH to the managed host and run sudo -l as the remote user to verify their sudo permissions.
4
Use --ask-become-pass if Required
If sudo requires a password, use -K or --ask-become-pass with your playbook command.
💡 Best Practice

Configure passwordless sudo for your Ansible service account on managed hosts. This simplifies automation and avoids the need to store or pass sudo passwords.

Ansible Logging

By default, Ansible is not configured to log its output to a log file. However, you can enable logging to help with troubleshooting and to maintain an audit trail.

Enabling Ansible Logging

Configure the log_path parameter in the [defaults] section of your ansible.cfg file:

ansible.cfg logging configuration
# ansible.cfg
[defaults]
inventory = ./inventory
remote_user = devops

# Enable logging
log_path = ./ansible.log
⚠️ File Permissions

The user running the playbook must have write permissions to the log file location. If the log file doesn't exist, Ansible will create it. If permissions are incorrect, logging will silently fail.

Log File Contents

The log file captures the same output you would see in the terminal, making it useful for:

  • Post-execution analysis of playbook runs
  • Auditing automation activities
  • Troubleshooting failed runs after the fact
  • Sharing execution details with team members
Example log output
2024-01-15 10:30:45,123 p=1234 u=student n=ansible | PLAY [Configure web servers] ***************
2024-01-15 10:30:45,456 p=1234 u=student n=ansible | TASK [Gathering Facts] *********************
2024-01-15 10:30:47,789 p=1234 u=student n=ansible | ok: [servera.lab.example.com]
2024-01-15 10:30:48,012 p=1234 u=student n=ansible | TASK [Install httpd] ************************
2024-01-15 10:30:52,345 p=1234 u=student n=ansible | changed: [servera.lab.example.com]

Environment Variable Alternative

You can also set the log path using the ANSIBLE_LOG_PATH environment variable:

Using environment variable
# Set log path for current session
$ export ANSIBLE_LOG_PATH=/var/log/ansible.log

# Run playbook with logging enabled
$ ansible-navigator run -m stdout playbook.yml

Common Errors

Learn to quickly identify and resolve the most common Ansible errors you'll encounter.

Error Quick Reference

Error TypeCommon CauseSolution
Syntax Error YAML indentation or quoting Use --syntax-check and fix indentation
UNREACHABLE SSH connection failed Check connectivity with ssh user@host
Permission Denied Missing sudo or become Add become: true and check sudoers
Undefined Variable Variable not defined Define in vars, defaults, or inventory
Module Not Found Typo or missing collection Use ansible-doc -l to verify module name

Undefined Variable Error

One of the most common errors occurs when referencing a variable that hasn't been defined:

Undefined variable error
fatal: [servera]: FAILED! => {"msg": "The task includes an option with an
undefined variable. The error was: 'package_name' is undefined"}
Solution: Define the variable
---
- name: Install package
  hosts: all
  vars:
    package_name: httpd  # Define the variable

  tasks:
    - name: Install the package
      ansible.builtin.dnf:
        name: "{{ package_name }}"
        state: present

Module Documentation

When you're unsure about module parameters or syntax, use ansible-doc:

Using ansible-doc
# List all available modules
$ ansible-doc -l

# View documentation for a specific module
$ ansible-doc ansible.builtin.copy

# Show just the examples
$ ansible-doc ansible.builtin.copy -s
💡 Troubleshooting Strategy

When debugging a playbook, follow this order: (1) Check syntax with --syntax-check, (2) Run with -v to see task results, (3) Add debug tasks for variables, (4) Use --check to preview changes, (5) Increase verbosity to -vvvv for connection issues.
