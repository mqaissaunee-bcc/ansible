Verbose Mode

Verbose mode provides progressively more detailed output about playbook execution, helping you understand exactly what Ansible is doing.

Verbosity Levels

Ansible supports four levels of verbosity, each providing more detail than the previous:

FlagLevelInformation Provided
-v Level 1 Task results and basic output
-vv Level 2 Input parameters and task configuration
-vvv Level 3 Connection details, SSH commands, file paths
-vvvv Level 4 Extra debugging including connection plugin scripts

Interactive Verbose Simulator

Select a verbosity level to see how the output changes:

Using Verbose Mode

Command line usage
# Basic verbose output
$ ansible-navigator run -m stdout playbook.yml -v

# Maximum verbosity for connection debugging
$ ansible-navigator run -m stdout playbook.yml -vvvv

# With ansible-playbook command
$ ansible-playbook playbook.yml -vvv
💡 Best Practice

Start with -v and increase verbosity only if needed. Level 4 (-vvvv) generates a lot of output and is best reserved for debugging complex connection issues.

The Debug Module

The ansible.builtin.debug module prints statements during playbook execution, making it invaluable for troubleshooting variable values and execution flow.

Basic Usage

Debug module examples
tasks:
  # Display a simple message
  - name: Show greeting message
    ansible.builtin.debug:
      msg: "Hello from {{ inventory_hostname }}"

  # Display a variable value
  - name: Show ansible_facts
    ansible.builtin.debug:
      var: ansible_facts['os_family']

  # Display with controlled verbosity
  - name: Show debug info only with -vv
    ansible.builtin.debug:
      msg: "Detailed debug information"
      verbosity: 2

Debug Parameters

ParameterDescriptionExample
msg Custom message to display (supports Jinja2) msg: "Value is {{ my_var }}"
var Variable name to display (no quotes or braces) var: ansible_hostname
verbosity Minimum verbosity level required to display verbosity: 2

Debugging Registered Variables

Use debug to inspect the structure of registered variablesVariables created using the register keyword that capture the output of a task, including stdout, stderr, return codes, and other metadata.:

Inspecting registered output
tasks:
  - name: Get service status
    ansible.builtin.command:
      cmd: systemctl status httpd
    register: service_result
    ignore_errors: true
    changed_when: false

  - name: Show full result structure
    ansible.builtin.debug:
      var: service_result

  - name: Show just the return code
    ansible.builtin.debug:
      msg: "Return code: {{ service_result.rc }}"

Interactive Debug Output Demo

Select debug type and click "Run Task" to see output...
⚠️ Important

The var parameter takes a variable name without quotes or curly braces. Using var: "{{ my_var }}" is incorrect and will cause unexpected results.

Syntax Checking

Validate your playbook syntax before execution to catch errors early and avoid wasted time on failed runs.

The --syntax-check Option

Use --syntax-check to validate YAML structure and Ansible syntax without executing any tasks:

Syntax check commands
# With ansible-navigator
$ ansible-navigator run -m stdout playbook.yml --syntax-check

# With ansible-playbook
$ ansible-playbook playbook.yml --syntax-check

# Successful output
playbook: playbook.yml

# Error output example
ERROR! Syntax Error while loading YAML.
  mapping values are not allowed in this context
The error appears to be in 'playbook.yml': line 10, column 12

Common Syntax Errors

🔴 Indentation Errors ▼

YAML requires consistent spacing. Never use tabs.

Error Example
ERROR! We were unable to read the playbook
mapping values are not allowed in this context
The error appears to be in 'playbook.yml': line 5
Solution

Use 2 spaces per indentation level. Check that all items at the same level have identical indentation.

🔴 Missing Quotes ▼

Values starting with {{ or containing special characters need quotes.

Wrong vs Correct
# Wrong - YAML syntax error
path: {{ doc_root }}/html

# Correct - quoted
path: "{{ doc_root }}/html"
Solution

Always quote values that start with {{ or contain colons, hashtags, or other special YAML characters.

🔴 Invalid Module Names ▼

Typos in module names or using deprecated names without the collection prefix.

Error Example
ERROR! couldn't resolve module/action 'coppy'
Solution

Use ansible-doc -l to list available modules. Always use FQCNs like ansible.builtin.copy.

🔴 Boolean Value Errors ▼

Using unquoted yes/no or true/false can cause issues in certain contexts.

Recommended Practice
# Recommended - explicit boolean
become: true
enabled: false

# Also valid but less clear
become: yes
enabled: no

Using ansible-lint

ansible-lintA linting tool that checks playbooks for best practices, deprecated syntax, and potential issues beyond basic syntax checking. goes beyond syntax checking to enforce best practices:

ansible-lint usage
# Install ansible-lint
$ pip install ansible-lint

# Run lint check
$ ansible-lint playbook.yml

# Example output
WARNING Listing 2 violation(s) that are fatal
playbook.yml:5 name[missing]: All tasks should be named.
playbook.yml:8 fqcn[action-core]: Use FQCN for builtin modules.

Check Mode and Diff

Preview changes before applying them with check mode (dry run) and see exactly what will change with diff mode.

Check Mode (Dry Run)

The --check option runs the playbook without making any changes, showing what would happen:

Check mode commands
# Basic check mode
$ ansible-navigator run -m stdout playbook.yml --check

# Check mode with diff to see changes
$ ansible-navigator run -m stdout playbook.yml --check --diff

# Using ansible-playbook
$ ansible-playbook playbook.yml --check --diff
⚠️ Check Mode Limitations

Tasks with check_mode: false will still execute in check mode. Additionally, command and shell modules cannot predict changes. Always inspect the playbook and any roles before trusting --check completely.

Controlling Check Mode Behavior

check_mode directive
tasks:
  # This task ALWAYS runs, even in check mode
  - name: Gather required information
    ansible.builtin.command:
      cmd: cat /etc/hostname
    register: hostname_result
    check_mode: false
    changed_when: false

  # This task ONLY runs in check mode
  - name: Validate configuration
    ansible.builtin.debug:
      msg: "Would configure {{ hostname_result.stdout }}"
    when: ansible_check_mode

The --diff Option

The --diff option shows line-by-line changes for file-modifying tasks:

--diff output example
TASK [Deploy configuration] ***************************
changed: [server1.example.com]
--- before: /etc/httpd/conf/httpd.conf
+++ after: /tmp/ansible_template.j2
- Listen 80
+ Listen 8080
- ServerAdmin root@localhost
+ ServerAdmin admin@example.com

Start-at-Task and Step Mode

Use these options to control which tasks execute during troubleshooting:

Targeted execution
# Start from a specific task
$ ansible-playbook playbook.yml --start-at-task="Install packages"

# Step through tasks one at a time (interactive)
$ ansible-playbook playbook.yml --step

# List all tasks without running
$ ansible-playbook playbook.yml --list-tasks

# List target hosts without running
$ ansible-playbook playbook.yml --list-hosts
💡 Pro Tip

The --step option prompts you before each task with (N)o/(y)es/(c)ontinue options. This is extremely useful for debugging complex playbooks.

Troubleshooting Connections

Many Ansible problems stem from connection issues to managed hosts. Learn to diagnose and resolve SSH authentication and connectivity problems.

Common Connection Errors

UNREACHABLE Error
TASK [Gathering Facts] *********************************
fatal: [host.example.com]: UNREACHABLE! => {"changed": false,
"msg": "Failed to connect to the host via ssh: Permission denied
(publickey,gssapi-keyex,gssapi-with-mic,password).",
"unreachable": true}

Connection Troubleshooting Checklist

1
Verify Basic Connectivity
ping hostname - Ensure network connectivity exists
ssh user@hostname - Test SSH connection manually
2
Check remote_user Setting
Verify remote_user in ansible.cfg or playbook matches a valid user on the managed host.
3
Validate SSH Keys
ssh-add -l - Check if SSH agent has your key
Verify public key is in ~/.ssh/authorized_keys on the managed host
4
Check Inventory Variables
Look for ansible_host, ansible_user, ansible_ssh_private_key_file overrides
5
Use Maximum Verbosity
ansible-playbook playbook.yml -vvvv - Shows full SSH connection details

Connection-Related Variables

VariableDescriptionExample
ansible_host IP or hostname to connect to ansible_host: 192.168.1.100
ansible_user SSH user for connection ansible_user: devops
ansible_ssh_private_key_file Path to SSH private key ~/.ssh/id_rsa
ansible_port SSH port number ansible_port: 2222
ansible_connection Connection type ansible_connection: local

Example: Fixing Inventory Issues

inventory file with connection settings
# Incorrect - using wrong host variable
[webservers]
serverb.lab.example.com ansible_host=serverc.lab.example.com  # Wrong!

# Correct inventory
[webservers]
serverb.lab.example.com

[webservers:vars]
ansible_user=devops

Privilege Escalation Issues

Many tasks require root privileges. Learn to troubleshoot privilege escalationThe process of gaining elevated permissions (typically root) to perform administrative tasks. Ansible uses 'become' to implement sudo, su, or other escalation methods. problems with become.

Common Privilege Escalation Errors

sudo password required
TASK [Install httpd] ***********************************
fatal: [server1]: FAILED! => {"msg": "Missing sudo password"}

Become Configuration

ansible.cfg become settings
# ansible.cfg
[privilege_escalation]
become = true
become_method = sudo
become_user = root
become_ask_pass = false

Playbook-Level Become

Using become in playbooks
---
- name: Configure web server
  hosts: webservers
  become: true              # Enable privilege escalation
  become_method: sudo      # Method (sudo, su, pbrun, etc.)
  become_user: root        # Target user

  tasks:
    - name: Install packages (requires root)
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Run as specific user
      ansible.builtin.command:
        cmd: whoami
      become_user: apache    # Override for this task

Troubleshooting Steps

✓
Verify the remote user has sudo privileges on the managed host
✓
Check /etc/sudoers for NOPASSWD configuration if not using --ask-become-pass
✓
Ensure become_method matches the system's escalation mechanism
✓
Use -K or --ask-become-pass if sudo requires a password
✓
Check for requiretty setting in sudoers (may need to disable)

Sudoers Configuration

Example /etc/sudoers entry
# Allow devops user to run all commands without password
devops ALL=(ALL) NOPASSWD: ALL

# Or for a specific group
%wheel ALL=(ALL) NOPASSWD: ALL
🔒 Security Note

While NOPASSWD is convenient for automation, consider the security implications. In production environments, use Ansible Vault to securely store become passwords, or use certificate-based authentication where possible.

Ansible Logging

Configure persistent logging to capture playbook execution details for later analysis and audit trails.

Enabling Log Files

By default, Ansible does not log to a file. Enable logging in ansible.cfg:

ansible.cfg logging configuration
[defaults]
# Enable logging to file
log_path = /var/log/ansible/ansible.log

# Alternative: log to project directory
log_path = ./ansible.log
⚠️ File Permissions

Ensure the user running Ansible has write permission to the log directory. Create the directory and set appropriate permissions before running playbooks.

Environment Variable

You can also set the log path using an environment variable:

Using ANSIBLE_LOG_PATH
# Set for current session
$ export ANSIBLE_LOG_PATH=/var/log/ansible/ansible.log

# Or set for a single command
$ ANSIBLE_LOG_PATH=./debug.log ansible-playbook playbook.yml -vvv

Log Output Example

/var/log/ansible/ansible.log
2024-01-15 10:23:45,123 p=12345 u=student n=ansible | PLAY [Configure servers] ***
2024-01-15 10:23:45,456 p=12345 u=student n=ansible | TASK [Gathering Facts] ***
2024-01-15 10:23:47,789 p=12345 u=student n=ansible | ok: [server1.example.com]
2024-01-15 10:23:48,012 p=12345 u=student n=ansible | TASK [Install httpd] ***
2024-01-15 10:23:52,345 p=12345 u=student n=ansible | changed: [server1.example.com]

Callback Plugins for Enhanced Output

Use callback plugins to change output format:

ansible.cfg callback configuration
[defaults]
# Change output format
stdout_callback = yaml

# Available callbacks: default, yaml, json, debug, minimal, dense

# Show task timing information
callbacks_enabled = ansible.posix.profile_tasks

Log Rotation

For production environments, configure log rotation to prevent disk space issues:

/etc/logrotate.d/ansible
/var/log/ansible/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 root root
}

Common Errors

Learn to quickly identify and resolve the most frequent Ansible errors.

Error Analysis Tool

Click on an error type to see examples and solutions:

YAML Syntax Errors

ERROR! Syntax Error while loading YAML.
  mapping values are not allowed in this context

The error appears to be in 'playbook.yml': line 8, column 12
Common Causes & Solutions
  • Tabs instead of spaces - YAML requires spaces only
  • Inconsistent indentation - Use 2 spaces per level consistently
  • Missing quotes - Quote values starting with {{ or containing :
  • Missing colons - Every key needs a colon followed by space

Module Errors

fatal: [server1]: FAILED! => {"changed": false, 
"msg": "Unsupported parameters for (copy) module: sources. 
Supported parameters include: attributes, backup, checksum, 
content, decrypt, dest, directory_mode..."}
Common Causes & Solutions
  • Typo in parameter name - Check spelling (src not sources)
  • Wrong module - Verify you're using the correct module
  • Missing required parameter - Some modules have required params
  • Version mismatch - Parameter may not exist in your Ansible version

Use ansible-doc module_name to see correct parameters.

Variable Errors

fatal: [server1]: FAILED! => {"msg": 
"The task includes an option with an undefined variable. 
The error was: 'my_variable' is undefined"}
Common Causes & Solutions
  • Typo in variable name - Check spelling carefully
  • Variable not defined - Define in vars, group_vars, or inventory
  • Wrong scope - Variable may be defined in different play/role
  • Facts not gathered - ansible_* vars need gather_facts: true

Use {{ my_var | default('fallback') }} for optional variables.

Template Errors

fatal: [server1]: FAILED! => {"changed": false,
"msg": "AnsibleError: template error while templating string: 
expected token 'end of print statement', got 'string'"}
Common Causes & Solutions
  • Missing quotes in template - Jinja2 strings need quotes
  • Syntax error in expression - Check Jinja2 syntax
  • Undefined filter - Verify filter exists
  • Missing closing braces - Match {{ with }}

Host/Inventory Errors

[WARNING]: Could not match supplied host pattern, ignoring: webservers
[WARNING]: No hosts matched, nothing to do
Common Causes & Solutions
  • Typo in hosts pattern - Check group/host names in inventory
  • Wrong inventory file - Specify with -i inventory
  • Empty group - Group exists but has no hosts
  • Host pattern syntax - Use correct pattern syntax

Use ansible-inventory --list to verify inventory contents.

Quick Reference: Error Resolution

Error TypeFirst StepCommand
Syntax Error Validate syntax ansible-playbook --syntax-check
Module Error Check documentation ansible-doc module_name
Connection Error Increase verbosity ansible-playbook -vvvv
Variable Error Debug variables Add debug: var=varname task
Host Error List inventory ansible-inventory --list

Hands-on Lab

Practice troubleshooting techniques with these guided exercises.

Lab 8.1 Debug a Failing Playbook

You have a playbook that fails during execution. Use the troubleshooting techniques learned to identify and fix the issues.

1
Create a playbook with intentional errors:
broken_playbook.yml
---
- name: Broken playbook example
  hosts: webservers
  become: true

  tasks:
    - name: Install package
      ansible.builtin.dnf:
        name: {{ package_name }}  # Missing quotes!
        state: present
2
Run syntax check to find the first error: 
$ ansible-playbook broken_playbook.yml --syntax-check
3
Fix the quoting issue and define the variable:
fixed_playbook.yml
---
- name: Fixed playbook example
  hosts: webservers
  become: true
  vars:
    package_name: httpd

  tasks:
    - name: Install package
      ansible.builtin.dnf:
        name: "{{ package_name }}"
        state: present
4
Test with check mode: 
$ ansible-playbook fixed_playbook.yml --check --diff -v
Lab 8.2 Troubleshoot Connection Issues

Diagnose and resolve a connection failure to a managed host.

1
Create an inventory with connection issues:
inventory
[webservers]
serverb.lab.example.com ansible_user=students  # Wrong user!
2
Run with high verbosity to identify the issue: 
$ ansible webservers -m ping -i inventory -vvvv
3
Review the verbose output to identify:
  • Which user is being used for connection
  • What authentication method is being tried
  • The exact error message

[webservers]

Lab 8.3 Use Debug Module Effectively

Add debugging statements to understand variable values and execution flow.

1
Create a playbook with debug tasks:
debug_example.yml
---
- name: Debug example playbook
  hosts: localhost
  gather_facts: true
  
  tasks:
    - name: Show OS family
      ansible.builtin.debug:
        var: ansible_facts['os_family']
    
    - name: Get disk usage
      ansible.builtin.command:
        cmd: df -h /
      register: disk_result
      changed_when: false
    
    - name: Show disk result structure
      ansible.builtin.debug:
        var: disk_result
    
    - name: Show only stdout lines
      ansible.builtin.debug:
        var: disk_result.stdout_lines
2
Run and observe the output structure: 
$ ansible-playbook debug_example.yml
